## 1. 定位与原则

- **记忆是灵魂，必须自研掌控**：M1–M3 全部由本项目实现；AgentScope 只做会话桥接，不承担长期记忆（其 v2 `LongTermMemory` 已标记 deprecated 并重写中，官方空窗期）。
- 单用户（v1.5 定稿）：服务**唯一用户本人**，不做多租户；`user_id` 仅作存储预留字段、**不作路由键**；首次启动引导初始化 `persona/` 文件（user.md / persona-config.yml 等，参考 OpenHanako）。
- 部署规模：个人服务器 / 小机器（约 2C4G），PostgreSQL 单机 + pgvector 足够，**不引入**独立向量库 / 图库。
- 隐私 L1/L2 从第一天生效：L2（敏感）只进本地模型链路，永不上云。
- 仓库按 public 安全标准维护：文档不出现公司名、个人路径、密钥。

### 1.1 存储选型评估：表 vs 文件（2026-09-07 定稿）

**结论：主存储用 PostgreSQL 表；Markdown / 文件只作人工调试导出与迁移工具，不是记忆真相源。**

结合本项目约束（单用户 + 小机器约 2C4G + "记忆不可丢"）逐维对比：

| 维度 | 本地文件（Markdown/JSON） | PostgreSQL 表 | 判给谁 | 说明 |
| :-- | :-- | :-- | :-- | :-- |
| 结构化查询 | 需全文扫描 + 正则，复杂过滤几乎不可能 | 原生 `WHERE type='PROFILE' AND attribute='city'` | **表** | 画像 / 偏好的属性级查询是日常操作 |
| bi-temporal 版本化 | 需手工维护多份历史文件，易混乱 | `valid_from/valid_to` + `history` 表，ACID 保证一致 | **表** | §6 已定稿 bi-temporal，表是实现前提 |
| 并发写入 | 多线程 / 多实例冲突，需文件锁 | 行锁 + MVCC | **表** | 写入管线与定时巡检会并发 |
| 向量检索 | 无法原生集成，需另维护索引文件 | pgvector 与正文同库同行 | **表** | 少维护一份双写存储 |
| 人工调试 | ✅ 可直接打开查看 / 编辑 | ❌ 需 SQL 查询 | **文件** | → 用「导出 .md 快照」满足（见下） |
| LLM 直读 | ✅ Agent 工具可直接读 | ❌ 需检索工具读 DB | **文件** | → 我们本就要求走 `MemoryPort` / 检索 API，不经文件 |

- **为什么放弃纯文件方案**：文件方案的"人工可读"优势，不值得换取结构化查询、版本化、并发与向量集成的代价；Jarvis 系已从"全文 Markdown 单行"迁移到 DB 表踩过此坑（§7）。本项目 M2/M3 需要去重、冲突、衰减、历史回溯等治理，文件系统上无法优雅实现。
- **文件在何时仍有用**：① 调试导出（从 DB dump 成 markdown 给人看）；② 一次性迁移工具（把历史文件导入 DB）。不对外暴露"文件心智"为存储，避免"LLM 直接改文件绕过治理"的旁路。


## 2. 分层模型（三层 + 两条横切管线）

| 层 | 名称 | 存储 | 内容 | 生命周期 |
| :-- | :-- | :-- | :-- | :-- |
| M1 | 短期记忆 | PostgreSQL（`session_message`）+ 进程内 | 会话消息记录（HTTP 读历史 / 写管线取源）+ AgentScope 运行态（AgentState，单实例进程内） | 会话内实时落库；会话结束归档 A1 后按策略降级/清理 |
| M2 | 结构化记忆 | PostgreSQL | 用户画像、偏好、重要事实（可查询、可版本化） | 跨会话持久，永久保留 |
| M3 | 语义记忆 | PostgreSQL + pgvector | 对话总结、事件、故事、非结构化片段 | 跨会话持久，按衰减策略降权（不删除） |

补充归档层（与 M3 互补，见 §3.4）：

| 层 | 名称 | 存储 | 内容 | 生命周期 |
| :-- | :-- | :-- | :-- | :-- |
| A1 | 会话归档 | PostgreSQL | 原始消息 JSON（按日分区） | 热 90 天 + 冷归档长期保留，不物理删除 |

横切：

- **写入管线（write pipeline）**：把"对话/事件"加工成 M2/M3/A1 记录的流水线，决定记忆质量的关键。
- **读取与注入（read/inject）**：每轮按需检索 M2/M3，受预算约束注入上下文。

> 结论（与业界对齐）：三层是 2025-26 主流标配；真正的差距不在存储选型，而在**写入管线精细化**与**可评测性**。

## 3. 存储与数据模型（草案）

### 3.1 M1 · PostgreSQL `session_message` + 进程内 AgentState（AgentScope 桥接）

M1 承担两类职责，**分开说清**：

1. **AgentScope 会话状态**（框架运行态：AgentState/上下文/工具/任务状态）
   - 单用户单实例下保持**进程内**（沿用现有 `InMemoryAgentStateStore`），**不做 Redis 化**——v1.5 已砍 Redis，AgentScope 官方 `AgentStateStore` 本就有内存 / PG 等实现可选。
   - ⚠️ P1 落地时实测确认：多轮 `agent.call` 在同一 `sessionId` 下自动衔接上下文（跨请求不丢）；若进程重启需恢复，P2 再评估 AgentState 是否随 M1 一并落 PG（预留 `openalice:` 前缀）。
2. **自研会话消息记录**（领域侧，供 HTTP 读历史 / 写管线取源）
   - 继续走 `core.MemoryPort`（`append/history`），P1 提供 `PgSessionMemoryPort`（表 `session_message`，会话消息实时落库）替换 `InMemoryMemoryPort`。
   - 表结构（规划）：`id / user_id(固定单用户，预留) / session_id / role / content jsonb / ts`，索引 `(user_id, session_id, ts)`；会话结束归档 A1 后，M1 明细按 §3.4 策略降级。

> 两者边界：AgentStateStore 管"框架怎么继续跑"（单实例进程内），MemoryPort 管"我们的记忆资产从哪来"（PG 落库）。不要混成一套。

### 3.2 M2 · PostgreSQL 结构化事实

```text
memory_fact
  id            uuid PK
  user_id       text          -- 固定单用户（预留扩展）
  type          text          -- PROFILE | PREFERENCE | FACT | DECISION
  subject       text          -- 事实主体（如“用户”“项目X”）
  attribute     text          -- 属性/谓词（如“居住城市”）
  value         text          -- 规范化后的值
  status        text          -- ACTIVE | SUPERSEDED（不物理删除）
  valid_from    timestamptz   -- bi-temporal：生效时间
  valid_to      timestamptz   -- 失效时间（默认 NULL = 当前有效）
  source_ref    jsonb         -- 来源会话/消息 id
  confidence    float         -- 置信度（供后续反馈调参）
  created_at / updated_at     -- 审计
memory_fact_history           -- 每次变更前的完整快照（追加式）
```

> 画像/偏好 = `type IN (PROFILE, PREFERENCE)` 的事实子集；**不单独拆 profile 表**，检索时用 type 限定 + 高优先级加权（§5），即可获得 Jarvis profile 的效果且结构更统一。

### 3.3 M3 · PostgreSQL + pgvector 语义记忆

```text
memory_episode
  id            uuid PK
  user_id       text
  kind          text          -- EVENT | STORY | NOTE（会话总结产物）
  content       text          -- 记忆正文（含绝对时间）
  embedding     vector(1536)  -- 维度随模型定（本地/云端 embedding）
  ts            timestamptz   -- 事件/对话时间
  hit_count     int           -- 命中次数
  last_hit_at   timestamptz   -- 最近命中（遗忘曲线衰减依据）
  decay_weight  float         -- 检索权重（随未命中时间下降）
  is_l2         bool          -- 敏感标记，仅本地链路可读
  created_at / updated_at
```

- 会话结束的**总结产物**（≈ Generative Agents 的 reflection）写入 M3；原始消息本身不进 M3，见 §3.4。
- 每天一条"每日回顾"NOTE 可选（对应 Jarvis daily.md 的按日期回档能力，用 kind + ts 检索即可，不单独建表）。

### 3.4 A1 · 会话归档表（原始消息回溯）

```text
session_archive
  id            uuid PK
  user_id       text
  session_id    text
  day           date          -- 按日分区
  seq           int           -- 会话内消息序号
  role          text          -- user | assistant
  content       jsonb         -- 原始消息（含附件/工具引用的序列化 JSON）
  ts            timestamptz
  PRIMARY KEY (user_id, session_id, day, seq)
```

- **写入时机**：会话结束（或达到归档阈值）时，先把原始消息 JSON 落 `session_archive`，再跑总结/抽取管线。
- **定位**：M3 管"语义检索"（不记得细节时模糊找），A1 管"精确时间点回溯"（"上周三聊的项目叫什么"→ 按日/按会话精确翻原文），两者互补。
- **保留策略（2026-09-07 确认）**：`session_archive` 按 `day` 分区——热分区保留 90 天供在线检索 / 精确回溯；超期分区迁移至冷归档（archive schema / 压缩存储，参考 pg_partman 的自动化分区迁移思路，**不 drop**），长期保留、**默认不物理删除**——与"记忆是灵魂、绝不丢失"的产品原则一致（单用户文本量小，成本可忽略）。
- **备份**：随每日备份一并覆盖，禁止因崩溃丢记忆。

## 4. 写入管线（Write Pipeline · 草案操作）

前置假设：**真实 LLM 已接入（P1 底座起）**——真实双 provider（中转站优先 + DeepSeek 官方兜底），抽取/分类/总结均由大模型驱动；不再设计 mock/规则引擎必经阶段（简单规则仅可作降级或离线自测选项）。

触发点（三选一并行）：

1. **会话结束总结**（主）：批处理式提炼整段会话 → 归档原文 + 产出结构化事实 + 事件笔记。
2. **会话内高价值点**（次）：用户显式"记住这个"/触发规则（决策、个人信息）时实时写入。
3. **每日/定时维护**（异步）：去重合并、衰减、备份。

### 4.1 步骤（核心操作）

| # | 操作 | 输入 → 输出 | 实现要点 |
| :-- | :-- | :-- | :-- |
| 0 | **归档 Archive** | 会话消息 → `session_archive` | 原始 JSON 按日落库，先归档后提炼，保证可回溯 |
| 1 | **抽取 Extract** | 对话/事件文本 → 候选记忆（事实/事件/偏好/决策/教训） | 一次 LLM 调用，输出 JSON；要求**绝对时间**，禁止相对时间 |
| 2 | **分类 Classify** | 候选 → `{type, L1/L2}` | type 映射 M2/M3；L2 标记隔离（仅本地 embedding/检索链路） |
| 3 | **规范化 Normalize** | 候选 → canonical form | 统一人称（"我"→用户）、实体、单位、时区、布尔/枚举值 |
| 4 | **查重 Dedup** | 候选 vs 既有 → `ADD / UPDATE / NOOP` | 语义相似度（cosine）> 0.85 视为同主题：正文一致→NOOP；互补→UPDATE 合并；**写侧去重是第一道闸** |
| 5 | **冲突解决 Conflict** | 同属性新旧值 → 裁决 | 建议 **bi-temporal**：新值 INSERT 并置 ACTIVE，旧值置 SUPERSEDED 且 `valid_to=now`，快照入 history；**不物理覆盖** |
| 6 | **写入 Store** | 裁决结果 → M2/M3 | M2：结构化行；M3：正文 + embedding + `last_hit_at` |
| 7 | **注入预备 Stage** | 本轮可注入项 → 候选池 | 供读取管线排序，不直接进 prompt |

### 4.2 定时维护任务（daily/idle）

- **去重合并巡检**：兜底查重，收敛碎片。
- **衰减降权（已采纳遗忘曲线）**：`decay_weight` 按未命中时长连续下调（可配半衰期，不删除）；检索命中即回拉并更新 `last_hit_at` / `hit_count`；**Profile / 偏好不参与衰减**（MemoryBank / 艾宾浩斯式，见 §6）。
- **备份**：每日全量备份（记忆禁止因崩溃丢失）。
- **回档**：daily 级别（按日）与 history 级别（按变更）双保险。

### 4.3 安全闸门

- **写入门控**：L2 候选 → 只允许写入 `is_l2=true` 且 embedding/检索限定**本地链路**（本地 / 自托管 embedding 模型，选型见 §9 待定）；云端模型永远看不到 L2 明文。
- **注入攻击防护（MINJA）**：外部内容（网页/文档）默认不可直接触发"写入"；写操作需用户参与或显式规则，防止提示注入污染长期记忆。

## 5. 读取与注入（Read / Inject）

1. **查询**：混合检索 = 语义（pgvector top-k）+ 关键词（pg_trgm/FTS）+ 时间/热度加权；M2 事实另走结构化条件（`type + attribute`）。
2. **排序**（草案公式）：

   ```text
   score = relevance × decay_weight × time_decay + type_priority_bonus
   ```

   - `type_priority_bonus`：`PROFILE / PREFERENCE` 给大额常驻加分（默认 +1000，可配置），确保"我叫什么/我住哪/核心偏好"这类基础事实**每轮几乎必进 Top-5**，不被遗忘曲线衰减挤掉。
   - 普通 `FACT / DECISION / M3` 正常走衰减。
3. **预算注入**：每轮 ≤ 5 条、合计 ≤ 800 token（硬约束，按序截断）。
4. **分域**：L1 记忆进云端对话上下文；L2 记忆只在本地会话注入；命中 L2 时模型侧只给占位提示（"存在本地敏感记忆，已省略"）。
5. 检索失败/空结果：显式降级，不打断主对话。

## 6. 治理规则（v1.4 定稿 · v1.5 沿用 · 需求书 §8.2）

> **2026-09-07 用户拍板**：下表修订项于《项目需求说明书》§8.2 **v1.4 定稿，v1.5 沿用未变**。「事实冲突」采纳 bi-temporal，「衰减归档」采纳遗忘曲线；其余项保留并明确落地形态。

| 治理项 | 需求书 §8.2（v1.2 原方案） | 定稿方案（v1.4） | 状态 |
| :-- | :-- | :-- | :-- |
| 事实冲突 | 新覆盖旧 + 变更历史 | **bi-temporal**：新值生效、旧值失效（SUPERSEDED + valid_to），快照进 history | ✅ 已采纳 |
| 去重合并 | 相似度 > 0.85 自动合并 | 保留 0.85 阈值；写侧查重第一道闸 + 定时巡检兜底 | ✅ 保留 |
| 注入预算 | ≤ 5 条 / ≤ 800 token | 保留（业界共识，硬约束） | ✅ 保留 |
| 衰减归档 | 180 天降权（不删除） | **遗忘曲线**：未命中时长连续降权 + 命中回拉；**Profile / 偏好不参与衰减**；不物理删除 | ✅ 已采纳 |
| 质量反馈 | 赞/踩调参 | 保留，落地为 confidence/hit 加权 | ✅ 保留 |

**bi-temporal 落地要点**：写入冲突时新值 INSERT 并置 ACTIVE，旧值置 SUPERSEDED 且 `valid_to = now`，变更前完整快照追加 `memory_fact_history`；查询默认过滤 `status='ACTIVE'`（见 §3.2 / §4.1 步骤 5）。

**遗忘曲线落地要点**：`decay_weight` 随 `last_hit_at` 未命中时长连续下降（可配半衰期），检索命中即回拉并更新 `last_hit_at` / `hit_count`；`type IN (PROFILE, PREFERENCE)` 不参与衰减（见 §3.2 / §4.2）。

## 7. 参考对照：Jarvis 系记忆实现（只作参考，不约束实现）

### 7.1 本地 Jarvis（本地工程代码实况）

- **会话层**：Spring AI ChatMemory 抽象；`SummaryChatMemory` 做 token 预算式滚动压缩（超限把旧消息摘要为一条 context），底层把整段消息 JSON 落库为会话 checkpoint。
- **长期/每日/资料层**：MD 语义、DB 行存储——long-term（全文一行的 markdown，章节级 READ/OVERRIDE/APPEND/DELETE）、daily（按 `yyyy-MM-dd` 每天一行全文）、profile（用户资料全文）；同构还有人格/规则文件落表；以 user + scene 隔离。
- **检索**：关键词 contains + 前后文片段截取（**无向量、无排序**）。
- **写入**：由 agent 自主调用工具（Agent-driven），**无抽取/去重/冲突/衰减/反馈管线**；长期记忆全凭 LLM 自律，OVERRIDE 即丢旧文。

### 7.2 企业内 Jarvis 变体（用户口述 v2026）

四层：① 短期上下文 = 数据库 + 内存，单次会话；② 长期记忆 `memory.md` = 数据库表，跨会话持久；③ 每日笔记 `daily.md` = 数据库表，按日期回档；④ 用户资料 `profile.md` = 数据库表，跨会话持久。

> 结论：**企业版与本地工程同源**——本地工程已落地同一套实现（MD 语义 + DB 表 + scene 隔离 + 会话压缩），两者描述与代码一一对应。

### 7.3 对 OpenAlice 的借鉴与差异

| 维度 | Jarvis（本地/企业） | OpenAlice 目标 | 说明 |
| :-- | :-- | :-- | :-- |
| 短期会话 | DB 整存整取 + 滚动摘要 | 进程内 AgentState（单实例）+ MemoryPort 落 PG 记录 | 框架状态与领域记录分开，摘要压缩思路可借鉴 |
| 会话回溯 | checkpoint 整存整取 | A1 `session_archive` 按日归档 | 保留可回溯性，且不塞进长期语义层 |
| 长期存储 | MD 全文单行存 DB | M2 结构化事实 + M3 向量记忆 | 放弃"全文 markdown 单行"，换取可查询/可版本化 |
| profile | 独立表/独立工具 | M2 的 `type=PROFILE` 子集 + 检索常驻高权重 | 检索层面等价，结构更统一 |
| 检索 | 关键词 contains | 语义 + 关键词 + 时间混合 + profile 加权 | 核心差距 |
| 写入 | LLM 自律 OVERRIDE/APPEND | 显式归档→抽取→分类→去重→冲突→衰减管线 | 核心差距（本草案 §4） |
| 纠错 | 覆盖即丢旧文 | bi-temporal + history | 更强可回滚 |
| 隔离 | scene_id | user_id + L1/L2 | 更强调隐私分域 |
| 文件心智 | MD 即文件（LLM 友好） | 不对外暴露"文件"，走端口 API + 调试导出 | 工程上更干净 |
