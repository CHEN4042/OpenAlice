## 1. 项目概述

| 项目名           | OpenAlice（A.L.I.C.E. · 爱丽丝）                                |
| :--------------- | :----------------------------------------------------------- |
| 项目定位         | AI陪伴助手——核心价值是**情绪陪伴 + 深度交互**                |
| 一句话描述       | 一个能随时陪你说话、记住你一切、有自己性格的AI智能体         |
| 目标用户         | **仅限本人**（第一版），轻度二次元、无日常社交、希望有人陪伴 |
| 开发周期         | 6个月                                                        |
| **项目灵感来源** | **[HomeRail](https://github.com/xiaotianfotos/homerail)** —— 语音优先的交互方式、生成式UI、DAG工作流编排 |

### 1.1 核心理念

- **"她是生活中的女主角"** —— 记忆是陪伴的灵魂，绝不允许AI忘记和用户之间的故事
- **"语音为主，文本兜底"** —— 像打电话一样自然，不方便时也能打字
- **"先有人，再有工具"** —— 先把陪伴体验做到极致，工具能力逐步扩展
- **"人的注意力是最稀缺的资源"** —— 系统应当尽量少地占用用户的注意力（借鉴 HomeRail）

### 1.2 交互设计原则（借鉴 HomeRail）

| 原则                 | 说明                                                         |
| :------------------- | :----------------------------------------------------------- |
| **语音优先**         | 语音是首选的交互方式，因为它对用户的注意力占用最少。用户说话，AI聆听、确认，在做任何事之前先消除模糊地带 |
| **生成式UI**         | AI不会把原始日志或JSON砸到用户面前，而是根据当下的情境，生成一份便于阅读和理解的可视化界面 |
| **可审计可追溯**     | 复杂任务的执行过程应可回放、可审计、可迭代优化               |
| **最小化注意力占用** | 一切自动化的目标都是让用户专注于创造性工作，而不是被系统打扰 |

## 3. 非功能需求

| 指标               | 目标值                           | 说明                                                         |
| :----------------- | :------------------------------- | :----------------------------------------------------------- |
| **语音响应延迟**   | **p95 < 3秒**                    | 半双工模式下，从检测到用户停止说话到首个可听音频。需记录测试设备、网络和模型版本 |
| **文本响应延迟**   | **首token p95 < 2秒**            | 从提交文本到收到首个流式token。**依赖 AgentScope 流式输出，见 Phase 1 验收** |
| **云服务器月成本** | **< 100元/月**                   | 2核4G轻量服务器（首版）                                      |
| **LLM方式**        | 开发用Ollama本地 + 正式用云端API | 双轨方案，灵活切换                                           |
| **LLM月成本**      | **目标 < 50元/月**               | 按实际token、ASR、TTS用量核算。超预算时自动切换本地模型或降级 |
| **可用性**         | 允许偶尔宕机                     | 个人使用，7x24非必须                                         |
| **记忆安全**       | **最高优先级**                   | 必须每日自动备份，支持快速恢复                               |
| **数据隐私**       | 两级分级控制                     | L1-一般记忆可上云；L2-敏感记忆默认本地保存（详见3.3节）      |

### 3.1 开发与部署策略

- **前3个月**：本地开发 + Ollama本地LLM + 文本/半双工语音 + 记忆闭环
- **后3个月**：Web UI、只读工具、云端部署、成本与恢复测试

### 3.2 安全需求（首版必须）★★★

Web UI 将通过公网访问，必须建立基础安全防线：

| 项目         | 首版方案                                                     |
| :----------- | :----------------------------------------------------------- |
| **访问认证** | 登录页 + 长随机Token（Session保持），防止URL泄露后被他人访问 |
| **传输加密** | 全站 HTTPS + WSS（Let's Encrypt 免费证书）                   |
| **密钥管理** | API Key 仅存环境变量（`OPENALICE_` 前缀），禁止提交Git，定期轮换  |
| **工具权限** | 文件操作限定白名单目录；命令执行需二次确认；**直接采用 AgentScope 2.0 权限系统（Permission System）+ workspace sandbox 作为底座** |
| **审计日志** | 工具调用全量日志，明确保留期限（至少30天）                   |

### 3.3 隐私分级方案

| 级别           | 定义               | 存储策略                             | 示例                                       |
| :------------- | :----------------- | :----------------------------------- | :----------------------------------------- |
| **L1（一般）** | 可上云的对话内容   | 云端LLM处理，API日志按供应商策略保留 | 天气查询、日常闲聊、知识问答               |
| **L2（敏感）** | 仅限本地处理的记忆 | 本地Ollama处理，不经过云端API        | 个人身份信息、健康数据、情绪隐私、家庭信息 |

**判定规则**：用户在创建记忆时可标记"私密"；系统自动对包含姓名、年龄、住址、健康数据的记忆标记为L2。

## 4. 技术选型

### 4.1 后端技术栈

| 层级            | 技术选型                                                | 说明                                                         |
| :-------------- | :------------------------------------------------------ | :----------------------------------------------------------- |
| **语言**        | Java 21                                                 | LTS版本，虚拟线程支持；AgentScope Java 2.0 要求 JDK 17+，满足 |
| **Agent 框架**  | **AgentScope Java 2.0（锁版本 2.0.0）** ★ 本版新增        | 阿里开源（2026-07 GA，生产就绪）：双层 Agent 架构（Harness 抽象）、事件流（event stream）、权限系统、中间件、workspace sandbox。GitHub：`agentscope-ai/agentscope-java`，文档：java.agentscope.io |
| **核心框架**    | Spring Boot 3 + Spring AI Alibaba                       | Spring Boot 3 应用接入 AgentScope 的官方推荐路径即经 Spring AI Alibaba（其内核正演进为 AgentScope）；Voice 能力继续由 Spring 生态承担 |
| **短期记忆**    | Redis                                                   | 会话上下文存储（`openalice:` 前缀）；桥接 AgentScope Memory 抽象  |
| **长期记忆**    | PostgreSQL + pgvector                                   | 结构化数据 + 向量语义搜索；三级记忆自研掌控                  |
| **LLM（开发）** | Ollama + Qwen2.5                                        | 本地免费，快速迭代；经 AgentScope Model 抽象接入             |
| **LLM（正式）** | 通义千问 / DeepSeek（待定）                             | 云端API，陪伴质量优先；DashScope 与 AgentScope 天然集成      |
| **语音方案**    | ASR + LLM + TTS 适配层                                  | 首版半双工；AgentScope 不覆盖语音链路，该适配层保持自研；浏览器音频格式（PCM或Opus）及服务端转码方案需在Phase 2明确 |
| **构建工具**    | Maven                                                   | 多模块管理（模块划分见 7.2）                                 |
| **云服务器**    | 腾讯云/阿里云轻量（2核4G）                              | 70-100元/月。⚠️ 内存紧张（Spring + AgentScope ~1G + PG ~1G + Redis + 系统），Phase 8前须做部署压测 |

### 4.2 前端技术栈

> **关键原则**：前端由AI全权负责开发，本人完全不参与。因此**优先选择AI训练数据最多、生成代码质量最高的技术栈**。

| 层级           | 技术选型          | 选择理由                         |
| :------------- | :---------------- | :------------------------------- |
| **框架**       | React 18+         | AI训练数据最丰富，生成代码最成熟 |
| **语言**       | TypeScript        | AI生成的类型安全代码更可靠       |
| **构建工具**   | Vite              | AI生成配置成熟，比CRA快10倍      |
| **UI组件库**   | shadcn/ui         | AI生成代码量最大的现代UI库       |
| **状态管理**   | Zustand           | 比Redux简单，AI生成代码稳定      |
| **HTTP客户端** | axios             | AI最熟悉的请求库                 |
| **WebSocket**  | 原生WebSocket API | AI生成标准API最可靠              |
| **语音录制**   | MediaRecorder API | 浏览器原生，AI生成成熟代码       |

### 4.3 通信协议

#### 设备 → 云服务器（WebSocket/HTTP）

```json
{
  "deviceId": "web_ui_001",
  "sessionId": "uuid",
  "contentType": "AUDIO_PCM" | "TEXT",
  "payload": "base64编码的音频 或 文本内容",
  "context": {
    "inputMode": "voice" | "text",
    "timestamp": "2026-08-17T10:00:00Z"
  }
}
```

#### 云服务器 → 设备（WebSocket）

```json
{
  "type": "TEXT_STREAM" | "AUDIO_STREAM" | "ACTION" | "UI_RENDER",
  "payload": "流式文本 或 音频数据 或 UI组件描述",
  "action": "SPEAK" | "DISPLAY" | "EXECUTE_TOOL" | "RENDER_UI",
  "sessionId": "uuid"
}
```

> **生成式UI扩展**：`type: "UI_RENDER"` 用于Agent生成可视化界面（如日程卡片、图表、控制面板），而非纯文本输出。
> **实现提示**：`TEXT_STREAM` 依赖 AgentScope 事件流（event stream）的 token 级转发，Phase 1 必须验证（见第 12 章）。

## 8. 记忆系统设计（三级架构）

| 层级               | 存储技术              | 内容                         | 特性                 |
| :----------------- | :-------------------- | :--------------------------- | :------------------- |
| **M1：短期记忆**   | Redis（`openalice:` 前缀） | 当前会话上下文               | 详细、完整、快速读写 |
| **M2：结构化记忆** | PostgreSQL            | 用户画像、偏好、重要事实     | 永久存储、结构化查询 |
| **M3：语义记忆**   | PostgreSQL + pgvector | 对话记录、故事、非结构化信息 | 向量化存储、语义搜索 |

> **与 AgentScope 的关系**：三级记忆由本项目**自研掌控**（记忆是项目灵魂，不外包给框架）；AgentScope 的 Memory 抽象仅作为桥接层对接 M1 会话上下文。

> **编号约定**：记忆层级编号 M1–M3（M = Memory），与第 3.3 节**隐私分级 L1/L2** 属于不同维度，二者不混用。

### 8.1 记忆管理原则

- **AI自动判断重要性**：会话结束后自动总结，判断哪些值得长期记忆
- **记忆注入Prompt**：将检索到的长期记忆自动注入到每次对话的上下文中
- **"短期详细，长期模糊"**：贴近人类真实记忆特征
- **用户可干预**：未来版本支持"记住这个"/"忘掉这个"手动标记
- **绝对安全**：每日自动备份，禁止因系统崩溃丢失记忆

### 8.2 记忆治理细则（v1.4 定稿）

> **v1.4 修订**：「事实冲突」→ bi-temporal；「衰减归档」→ 遗忘曲线（连续衰减 + 命中回拉）。本表为定稿方案，详细数据模型与写入管线见《记忆架构设计 v0.3》§3 / §4 / §6。

| 治理项       | 首版方案（v1.2）                                          | 定稿方案（v1.4，2026-09-07 拍板）                          |
| :----------- | :--------------------------------------------------------- | :--------------------------------------------------------- |
| **事实冲突** | 新信息覆盖旧信息，旧值存入变更历史（如"用户换了工作城市"） | **bi-temporal**：新值生效（ACTIVE）、旧值失效（SUPERSEDED + `valid_to`），变更前快照追加 `memory_fact_history`；不物理覆盖，可回滚 / 审计 |
| **去重合并** | 向量相似度 > 0.85 的记忆自动合并                           | 保留 0.85 阈值；写侧查重为第一道闸（ADD / UPDATE / NOOP），定时巡检兜底 |
| **注入预算** | 每次对话注入记忆 ≤ 5 条、合计 ≤ 800 token（按相关度排序）  | 保留（硬约束，按序截断）                                   |
| **衰减归档** | 180天未命中的语义记忆降权（不删除，降低检索优先级）        | **遗忘曲线**：按未命中时长连续降权 + 命中回拉；用户画像 / 偏好不参与衰减；语义记忆永不物理删除 |
| **质量反馈** | 用户可对检索结果点"赞/踩"，用于后续调参                    | 保留，落地为 `confidence` / `hit` 加权                    |

**bi-temporal（双时态）为何采用**：事实更新不再"覆盖即丢旧文"，而是让新旧值各带**生效时间（`valid_from` / `valid_to`）**，旧值仅标记失效并保留快照。代价是写入多一步、查询多一个 `status='ACTIVE'` 条件；换来**可回滚、可审计、可回答"你以前在哪上班"这类历史问题**——对"永不忘记"的陪伴型 AI 是核心能力而非负担。

**遗忘曲线为何替代 180 天一刀切**：固定 180 天降权过于生硬（第 179 天还正常、第 181 天突然沉底）。改为**连续衰减 + 命中回拉**（借鉴 MemoryBank / 艾宾浩斯）：越久未命中权重越低，一旦被检索命中即回拉、后续更容易被想起——更接近人类记忆；用户画像 / 核心偏好永不衰减。

### 8.3 存储选型与归档（v1.4 新增）

- **主存储 = PostgreSQL 表**（结构化记忆 / 语义记忆 / 会话归档同一套库）：原生结构化查询、bi-temporal 版本化与并发安全（ACID / MVCC）、pgvector 向量与正文同库同行——单用户小机器（约 2C4G）一个 PG 实例足够，不引入独立向量库 / 图库。
- **文件只作辅助**：Markdown / 文件快照仅用于**人工调试导出与迁移工具**，不是主存储、不是记忆真相源（评估细节见《记忆架构设计 v0.3》§1.1）。
- **A1 会话归档层**：会话结束先归档原始消息（`session_archive`，按日分区）再跑总结 / 抽取管线；热分区保留 90 天供在线回溯，超期迁冷归档**长期保留、默认不物理删除**——与"记忆是灵魂、绝不丢失"原则一致，单用户文本量成本可忽略。

## 9. 容错与降级链路

| 故障场景             | 处理策略                                                   |
| :------------------- | :--------------------------------------------------------- |
| **云端LLM超时/报错** | 自动切换本地Ollama，回复："网络不太稳，我用简版模式陪你聊" |
| **ASR识别置信度低**  | 返回澄清话术，两次失败后建议切换文本输入                   |
| **TTS合成失败**      | 文本照常输出，标注"语音生成失败，请查看文字"               |
| **WebSocket断线**    | 客户端自动重连，30秒内恢复会话上下文                       |
| **记忆检索超时**     | 跳过注入，不阻塞回复                                       |
| **数据库连接失败**   | 降级到内存缓存，重启后恢复                                 |
| **AgentScope升级异常** ★ | **锁版本 2.0.0；升级前在 `dev` 分支跑全量回归（重点：流式输出）** |

## 10. 成本模型

### 10.1 月消耗量假设（高强度使用场景）

| 项目          | 日均用量 | 月均用量 | 备注                       |
| :------------ | :------- | :------- | :------------------------- |
| 对话轮数      | 20轮     | 600轮    | 按每天30分钟互动估算       |
| 每轮输入token | 2000     | —        | 含历史对话上下文注入       |
| 每轮输出token | 500      | —        | —                          |
| 月总token     | —        | 150万    | 600 × (2000 + 500) = 150万 |
| 语音输入      | 15分钟   | 450分钟  | 日均15分钟语音对话         |
| 语音输出      | 15分钟   | 450分钟  | 等量TTS输出                |

### 10.2 月成本计算公式

```
月成本 = LLM费用 + ASR费用 + TTS费用

LLM费用 = (月输入tokens × 输入单价 + 月输出tokens × 输出单价) × 缓存命中率折扣
ASR费用 = 月语音分钟数 × 分钟单价
TTS费用 = 月语音输出字符数 × 字符单价
```

**首版目标**：月总成本 < 50元（不含云服务器硬件成本）

### 10.3 成本控制机制

- 月预算达到80%时，系统发送预警通知
- 用户可手动切换至本地Ollama或降级模型
