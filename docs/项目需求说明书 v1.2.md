## 1. 项目概述

| 项目名           | OpenAlice（A.L.I.C.E. · 爱丽丝）                                |
| :--------------- | :----------------------------------------------------------- |
| 项目定位         | AI陪伴助手——核心价值是**情绪陪伴 + 深度交互**                |
| 一句话描述       | 一个能随时陪你说话、记住你一切、有自己性格的AI智能体         |
| 目标用户         | **仅限本人**（第一版），轻度二次元、无日常社交、希望有人陪伴 |
| 开发周期         | 按 P1–P4 分阶段推进（原 6 个月为参考目标，节奏以实际为准）      |
| **项目灵感来源** | **[HomeRail](https://github.com/xiaotianfotos/homerail)** —— 语音优先的交互方式、生成式UI、DAG工作流编排 |

### 1.1 核心理念

- **"她是生活中的女主角"** —— 记忆是陪伴的灵魂，绝不允许AI忘记和用户之间的故事
- **"语音为主，文本兜底"**（愿景）——像打电话一样自然，不方便时也能打字；**P1–P2 以文本为主，语音在 P3 落地**
- **"先有人，再有工具"** —— 先把陪伴体验做到极致，工具能力逐步扩展
- **"人的注意力是最稀缺的资源"** —— 系统应当尽量少地占用用户的注意力（借鉴 HomeRail）

### 1.2 交互设计原则（借鉴 HomeRail）

| 原则                 | 说明                                                         |
| :------------------- | :----------------------------------------------------------- |
| **语音优先**         | 语音是首选的交互方式（**愿景，P3 起落地**；P1–P2 以文本对话为主）。用户说话，AI聆听、确认，在做任何事之前先消除模糊地带 |
| **生成式UI**         | AI不会把原始日志或JSON砸到用户面前，而是根据当下的情境生成可视化界面（**P4 起落地**） |
| **可审计可追溯**     | 复杂任务的执行过程应可回放、可审计、可迭代优化               |
| **最小化注意力占用** | 一切自动化的目标都是让用户专注于创造性工作，而不是被系统打扰 |

## 2. 功能需求

### 2.1 阶段坐标定义（v1.5 起）

> 能力 / 功能的落地顺序统一用**阶段坐标 P1–P4** 表达（P = Phase）。v1.5 起废弃原「功能优先级 P0/P1/P2」标记，功能归属直接并入阶段坐标，避免与阶段 P 编号混淆（功能表 §2.2 的「优先级」列已改为「落地阶段」）。

| 阶段 | 名称 | 一句话 | 典型范围 |
| :-- | :-- | :-- | :-- |
| **P1** | 会说真话（底座） | 接真实 LLM、能持续对话、会话不丢 | 真实双 provider + `/chat` SSE 流式 + PG 会话持久化（M1）+ 单用户 `persona/` 初始化 + 人格基调 |
| **P2** | 记得住 | 记忆闭环 | M1–M3 + A1 会话归档 + 写入 / 读取管线 + 混合检索 + 治理（bi-temporal / 遗忘曲线 / 反馈） |
| **P3** | 听得到 | 语音交互 | 半双工语音（ASR + LLM + TTS），WebSocket 前向通路，文本兜底 |
| **P4** | 看得见 / 摸得到 | 界面与行动能力 | Web UI、工具调用（MCP 只读工具起）、主动推送、生成式 UI、多设备 |
| **暂缓** | 留扩展空间 | 短期无明确排期 | 多用户、多人格、日程 / 健康 / 智能家居、屏幕读取、手机 / 手表 App 等 |

> 设计原则：**P1 打底座，能砍则砍**——P1 只放"明显盖棺定论"的最小闭环（真实模型、流式文本、会话持久化、单用户初始化）；其余能力一律后置到 P2–P4，避免中途返工。每个阶段完成并验收后再进入下一阶段；不设硬性周排期（原 6 个月为参考目标，见 §12）。

### 2.2 功能清单（按落地阶段归属）

| 功能模块 | 落地阶段 | 说明 |

| **文件管理** | **暂缓** | P4 及以后，AI 帮你创建 / 读取 / 整理本地文档 |

## 3. 非功能需求

| 指标               | 目标值                           | 说明                                                         |
| :----------------- | :------------------------------- | :----------------------------------------------------------- |
| **语音响应延迟**   | **p95 < 3秒**（P3 起验收）       | 半双工模式下，从检测到用户停止说话到首个可听音频。需记录测试设备、网络和模型版本 |
| **文本响应延迟**   | **首token p95 < 2秒**（P1 起验收）| 从提交文本到收到首个流式 token。**P1 起 `/chat` 走 SSE 流式；依赖 AgentScope 流式输出，见 §12 P1 验收** |
| **云服务器月成本** | **< 100元/月**                   | 2核4G轻量服务器（首版）                                      |
| **LLM方式**        | 真实模型双 provider：**中转站（OpenAI 兼容，优先）** + **DeepSeek 官方 API（兜底）** | 同协议仅 base_url / key 不同，故障自动切换；密钥走 `OPENALICE_*` 环境变量，不落盘 |
| **LLM月成本**      | **目标 < 50元/月**               | 按实际token、ASR、TTS用量核算。超预算时自动降级 / 切换 provider（DeepSeek 官方兜底） |
| **可用性**         | 允许偶尔宕机                     | 个人使用，7x24非必须                                         |
| **记忆安全**       | **最高优先级**                   | 必须每日自动备份，支持快速恢复                               |
| **数据隐私**       | 两级分级控制                     | L1-一般记忆可上云；L2-敏感记忆默认本地保存（详见3.3节）      |

### 3.1 开发与部署策略

- **P1（会说真话）**：本地开发 + 真实模型（中转站优先）+ 文本 SSE 流式对话 + PG 会话持久化 + persona/ 初始化
- **P2（记得住）**：记忆闭环（M1–M3 + A1 归档 + 写入 / 读取管线）
- **P3（听得到）**：半双工语音 + WebSocket 前向通路
- **P4（看得见 / 摸得到）**：Web UI、只读工具、云端部署、成本与恢复测试

### 3.2 安全需求（P4 Web UI 上线前必须；P1 先打底）★★★

Web UI 上线（P4）后将通过公网访问，必须建立基础安全防线；P1–P3 本机 / 内网运行阶段先落地「密钥管理」「工具权限」「审计日志」三条底线：

| 项目         | 首版方案                                                     |
| :----------- | :----------------------------------------------------------- |
| **访问认证** | 登录页 + 长随机 Token（Session 保持），防止 URL 泄露后被他人访问（P4 Web UI 上线时落地；P1–P3 默认仅绑定 localhost / 内网） |
| **传输加密** | 全站 HTTPS + WSS（Let's Encrypt 免费证书）（P4 公网部署时落地） |
| **密钥管理** | API Key 仅存环境变量（`OPENALICE_` 前缀），禁止提交Git，定期轮换  |
| **工具权限** | 文件操作限定白名单目录；命令执行需二次确认；**直接采用 AgentScope 2.0 权限系统（Permission System）+ workspace sandbox 作为底座**（随 P4 工具能力落地） |
| **审计日志** | 工具调用全量日志，明确保留期限（至少30天）                   |

### 3.3 隐私分级方案

| 级别           | 定义               | 存储策略                             | 示例                                       |
| :------------- | :----------------- | :----------------------------------- | :----------------------------------------- |
| **L1（一般）** | 可上云的对话内容   | 云端LLM处理，API日志按供应商策略保留 | 天气查询、日常闲聊、知识问答               |

### 4.3 通信协议

#### 文本对话（P1 起）：HTTP POST + SSE 流式

- 客户端 `POST /api/v1/chat`（`{sessionId, message}`）→ 服务端返回 `text/event-stream`。
- **P1 起直接走流式，不做同步 JSON 先行**：把 AgentScope 事件流（token 级）原样转成 SSE 事件下发。
- P1 为单用户：请求无需 `userId` 路由（服务端固定），`userId` 仅作存储预留字段。

服务端 → 客户端事件（v1 最小集；向后兼容，未知事件忽略）：

| event | data 示例 | 说明 |
| :-- | :-- | :-- |
| `text_delta` | `{"delta":"..."}` | 增量文本（逐 token / 逐块） |
| `done` | `{"sessionId":"...","messageId":"..."}` | 本轮正常结束 |
| `error` | `{"code":"...","message":"..."}` | 异常 / provider 降级提示 |

> 扩展位（只增不改）：P2 加 `memory_hit`（记忆注入提示）、P4 加 `tool_call` / `ui_render`。
> 请求示例：`{"sessionId":"default","message":"你好"}`。

#### 语音对话（P3 起）：WebSocket 双向

语音阶段（P3）由 WebSocket 承载音频与打断；下方 JSON 信封继续沿用，`TEXT_STREAM` 语义与 SSE `text_delta` 一致。

##### 设备 → 云服务器（WebSocket）

```json
{
  "deviceId": "web_ui_001",
  "sessionId": "uuid",
  "contentType": "AUDIO_PCM" | "TEXT",
  "payload": "base64编码的音频 或 文本内容",
  "context": {
    "inputMode": "voice" | "text",
    "timestamp": "2026-08-17T10:00:00Z"
  }
}
```

##### 云服务器 → 设备（WebSocket）

```json
{
  "type": "TEXT_STREAM" | "AUDIO_STREAM" | "ACTION" | "UI_RENDER",
  "payload": "流式文本 或 音频数据 或 UI组件描述",
  "action": "SPEAK" | "DISPLAY" | "EXECUTE_TOOL" | "RENDER_UI",
  "sessionId": "uuid"
}
```

> **生成式UI扩展**（P4）：`type: "UI_RENDER"` 用于 Agent 生成可视化界面（如日程卡片、图表、控制面板），而非纯文本输出。
> **实现提示**：流式输出依赖 AgentScope 事件流（event stream）的 token 级转发，**P1 必须验证**（见 §12 P1 验收）。

## 5. 人格设定

### 5.1 初始人格风格（v1.3：人格条目与名字解耦，可后续调整）

**温柔陪伴型**（人格基调，可后续调整）：

- **倾听**：轻声细语、先听完再回应
- **共情 / 呵护**：善解人意、会安慰人、有耐心

## 8. 记忆系统设计（三级架构）

| 层级               | 存储技术              | 内容                         | 特性                 |
| :----------------- | :-------------------- | :--------------------------- | :------------------- |
| **M1：短期记忆**   | PostgreSQL + 进程内       | 会话消息记录（实时落库）+ AgentScope 运行态（AgentState） | 详细、完整、会话不丢 |
| **M2：结构化记忆** | PostgreSQL            | 用户画像、偏好、重要事实     | 永久存储、结构化查询 |
| **M3：语义记忆**   | PostgreSQL + pgvector | 会话总结产物、事件、故事、非结构化片段 | 向量化存储、语义搜索 |

> **与 AgentScope 的关系**：三级记忆由本项目**自研掌控**（记忆是项目灵魂，不外包给框架）。M1 会话消息经 `port.MemoryPort`（append/history）实时落 PG；AgentScope 的 AgentState 运行态在单实例下保持进程内（`InMemoryAgentStateStore`），**暂不做 Redis 化**——如需跨实例 / 跨进程恢复会话再引入（预留 `openalice:` 前缀）。

> **编号约定**：记忆层级编号 M1–M3（M = Memory），与第 3.3 节**隐私分级 L1/L2** 属于不同维度，二者不混用。

### 8.1 记忆管理原则

- **AI自动判断重要性**：会话结束后自动总结，判断哪些值得长期记忆
- **记忆注入Prompt**：将检索到的长期记忆自动注入到每次对话的上下文中
- **"短期详细，长期模糊"**：贴近人类真实记忆特征
- **用户可干预**：未来版本支持"记住这个"/"忘掉这个"手动标记
- **绝对安全**：每日自动备份，禁止因系统崩溃丢失记忆

### 8.2 记忆治理细则（v1.4 定稿）

> **v1.4 修订**：「事实冲突」→ bi-temporal；「衰减归档」→ 遗忘曲线（连续衰减 + 命中回拉）。本表为定稿方案，详细数据模型与写入管线见《记忆架构设计 v0.4》§3 / §4 / §6。

| 治理项       | 首版方案（v1.2）                                          | 定稿方案（v1.4，2026-09-07 拍板）                          |
| :----------- | :--------------------------------------------------------- | :--------------------------------------------------------- |
| **事实冲突** | 新信息覆盖旧信息，旧值存入变更历史（如"用户换了工作城市"） | **bi-temporal**：新值生效（ACTIVE）、旧值失效（SUPERSEDED + `valid_to`），变更前快照追加 `memory_fact_history`；不物理覆盖，可回滚 / 审计 |
| **去重合并** | 向量相似度 > 0.85 的记忆自动合并                           | 保留 0.85 阈值；写侧查重为第一道闸（ADD / UPDATE / NOOP），定时巡检兜底 |
| **注入预算** | 每次对话注入记忆 ≤ 5 条、合计 ≤ 800 token（按相关度排序）  | 保留（硬约束，按序截断）                                   |
| **衰减归档** | 180天未命中的语义记忆降权（不删除，降低检索优先级）        | **遗忘曲线**：按未命中时长连续降权 + 命中回拉；用户画像 / 偏好不参与衰减；语义记忆永不物理删除 |
| **质量反馈** | 用户可对检索结果点"赞/踩"，用于后续调参                    | 保留，落地为 `confidence` / `hit` 加权                    |

**bi-temporal（双时态）为何采用**：事实更新不再"覆盖即丢旧文"，而是让新旧值各带**生效时间（`valid_from` / `valid_to`）**，旧值仅标记失效并保留快照。代价是写入多一步、查询多一个 `status='ACTIVE'` 条件；换来**可回滚、可审计、可回答"你以前在哪上班"这类历史问题**——对"永不忘记"的陪伴型 AI 是核心能力而非负担。

**遗忘曲线为何替代 180 天一刀切**：固定 180 天降权过于生硬（第 179 天还正常、第 181 天突然沉底）。改为**连续衰减 + 命中回拉**（借鉴 MemoryBank / 艾宾浩斯）：越久未命中权重越低，一旦被检索命中即回拉、后续更容易被想起——更接近人类记忆；用户画像 / 核心偏好永不衰减。

### 8.3 存储选型与归档（v1.4 新增）

- **主存储 = PostgreSQL 表**（结构化记忆 / 语义记忆 / 会话归档同一套库）：原生结构化查询、bi-temporal 版本化与并发安全（ACID / MVCC）、pgvector 向量与正文同库同行——单用户小机器（约 2C4G）一个 PG 实例足够，不引入独立向量库 / 图库。
- **文件只作辅助**：Markdown / 文件快照仅用于**人工调试导出与迁移工具**，不是主存储、不是记忆真相源（评估细节见《记忆架构设计 v0.4》§1.1）。
- **A1 会话归档层**：会话结束先归档原始消息（`session_archive`，按日分区）再跑总结 / 抽取管线；热分区保留 90 天供在线回溯，超期迁冷归档**长期保留、默认不物理删除**——与"记忆是灵魂、绝不丢失"原则一致，单用户文本量成本可忽略。
- **M1 会话消息入 PG（v1.5）**：会话期消息实时写入 `session_message`（经 MemoryPort 落库），会话结束归档进 A1 后，M1 明细按策略降级。**Redis 砍单**：M1 不再依赖独立缓存，如需会话级缓存或跨实例状态再按需引入（前缀沿用 `openalice:`）。
- **基础设施收敛（v1.5）**：唯一外部存储 = PostgreSQL（pgvector）；不再起本地 Ollama 模型服务，模型统一走真实双 provider。

## 9. 容错与降级链路

| 故障场景             | 处理策略                                                   |
| :------------------- | :--------------------------------------------------------- |
| **LLM 超时 / 报错**  | 自动切换 **DeepSeek 官方兜底**（中转站优先）；双 provider 都失败则返回降级话术并保留消息待重试 |
| **ASR识别置信度低**  | 返回澄清话术，两次失败后建议切换文本输入                   |
| **TTS合成失败**      | 文本照常输出，标注"语音生成失败，请查看文字"               |
| **SSE 断线 / 重连**   | 客户端自动重连；必要时用历史接口（GET messages）30 秒内恢复会话上下文 |
| **记忆检索超时**     | 跳过注入，不阻塞回复                                       |
| **数据库连接失败**   | 降级到内存缓存，重启后恢复                                 |
| **AgentScope升级异常** ★ | **锁 2.0.2（回退线 2.0.0）；升级前在 `dev` 分支跑全量回归（重点：SSE 流式输出）** |

## 10. 成本模型

### 10.1 月消耗量假设（高强度使用场景）

| 项目          | 日均用量 | 月均用量 | 备注                       |
| :------------ | :------- | :------- | :------------------------- |
| 对话轮数      | 20轮     | 600轮    | 按每天30分钟互动估算       |
| 每轮输入token | 2000     | —        | 含历史对话上下文注入       |
| 每轮输出token | 500      | —        | —                          |
| 月总token     | —        | 150万    | 600 × (2000 + 500) = 150万 |
| 语音输入      | 15分钟   | 450分钟  | 日均15分钟语音对话         |
| 语音输出      | 15分钟   | 450分钟  | 等量TTS输出                |

### 10.2 月成本计算公式

```
月成本 = LLM费用 + ASR费用 + TTS费用

LLM费用 = (月输入tokens × 输入单价 + 月输出tokens × 输出单价) × 缓存命中率折扣
ASR费用 = 月语音分钟数 × 分钟单价
TTS费用 = 月语音输出字符数 × 字符单价
```

**首版目标**：月总成本 < 50元（不含云服务器硬件成本）

### 10.3 成本控制机制

- 月预算达到80%时，系统发送预警通知
- 用户可手动切换 provider（中转站 ↔ DeepSeek 官方）或降级模型

## 12. 开发里程碑（按能力分阶段 P1–P4）

> v1.5 起阶段坐标统一为 **P1–P4**（替代 v1.4 的 Phase 1–9 周排期）：每个阶段打底并验收后再进入下一阶段；不设硬性周排期，原 6 个月为参考目标。

| 阶段 | 名称 | 内容 | 关键验收 |
| :-- | :-- | :-- | :-- |
| **P1** | 会说真话（底座） | 真实双 provider 接入（中转站优先 + DeepSeek 兜底）；`/chat` SSE 流式；M1 会话消息 PG 持久化（重启不丢）；单用户 persona/ 初始化；人格基调注入 | ① curl / 简易测试页多轮对话，SSE token 级流式返回（首 token p95 < 2s）；② provider 故障自动切换兜底；③ 进程重启后可从 PG 恢复会话历史；④ 首次启动引导生成 persona/ 文件 |
| **P2** | 记得住 | M2（memory_fact/history）+ M3（pgvector 总结）+ A1（session_archive）+ 写入 / 读取管线 + 混合检索 + 治理（bi-temporal / 遗忘曲线 / 反馈） | 画像 / 偏好 / 事实端到端写入与历史回滚；跨会话问答（"我叫什么 / 上周聊的项目"）；记忆注入预算生效 |
| **P3** | 听得到 | 半双工语音（ASR + LLM + TTS）+ WebSocket 前向通路 + VAD 断句 | 点按说话 → 松开 → 可听音频回复，延迟 p95 < 3s；文本兜底可用 |
| **P4** | 看得见 / 摸得到 | Web UI（认证 + 双语 Logo + 生成式 UI 基础）+ 只读工具（MCP 天气 / 时间）+ 主动推送 + 云端部署 + 成本与恢复验证 | 浏览器可用；工具调用闭环；部署后压测与备份恢复通过 |

> 记忆、语音、Web 的详细落地拆解分别见《记忆架构设计 v0.4》、§6.3 与 §4.3；每个阶段预留 10%~20% 缓冲应对技术障碍（以 AgentScope 实测为准）。
