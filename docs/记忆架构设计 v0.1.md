## 1. 定位与原则

- **记忆是灵魂，必须自研掌控**：M1–M3 全部由本项目实现；AgentScope 只做会话桥接，不承担长期记忆（其 v2 `LongTermMemory` 已标记 deprecated 并重写中，官方空窗期）。
- 单用户陪伴型 AI：先服务**唯一用户本人**，不做多租户 SaaS；但仍保留 `user_id` 维度，给未来多用户/多场景留口。
- 部署规模：个人服务器 / 小机器（约 2C4G），PostgreSQL 单机 + pgvector 足够，**不引入**独立向量库 / 图库。
- 隐私 L1/L2 从第一天生效：L2（敏感）只进本地模型链路，永不上云。
- 仓库按 public 安全标准维护：文档不出现公司名、个人路径、密钥。

## 2. 分层模型（三层 + 两条横切管线）

| 层 | 名称 | 存储 | 内容 | 生命周期 |
| :-- | :-- | :-- | :-- | :-- |
| M1 | 短期记忆 | Redis + 进程内 | 当前会话上下文、会话摘要占位 | 会话内快速读写；会话结束提炼后清理/降级 |
| M2 | 结构化记忆 | PostgreSQL | 用户画像、偏好、重要事实（可查询、可版本化） | 跨会话持久，永久保留 |
| M3 | 语义记忆 | PostgreSQL + pgvector | 对话事件、故事、非结构化片段 | 跨会话持久，按衰减策略降权（不删除） |

横切：

- **写入管线（write pipeline）**：把"对话/事件"加工成 M2/M3 记录的流水线，决定记忆质量的关键。
- **读取与注入（read/inject）**：每轮按需检索 M2/M3，受预算约束注入上下文。

> 结论（与业界对齐）：三层是 2025-26 主流标配；真正的差距不在存储选型，而在**写入管线精细化**与**可评测性**。

## 3. 存储与数据模型（草案）

### 3.1 M1 · Redis（`openalice:` 前缀）

- `openalice:session:{userId}:{sessionId}`：消息列表 / 游标；TTL = 会话 TTL。
- `openalice:summary:{userId}:{sessionId}`：会话滚动摘要（供续聊快速恢复）。
- 进程内仅做热缓存，Redis 为权威；Redis 不可用可回退纯内存（Phase 1 现状）。

### 3.2 M2 · PostgreSQL 结构化事实

```text
memory_fact
  id            uuid PK
  user_id       text          -- 预留多用户
  type          text          -- PROFILE | PREFERENCE | FACT | DECISION
  subject       text          -- 事实主体（如“用户”“项目X”）
  attribute     text          -- 属性/谓词（如“居住城市”）
  value         text          -- 规范化后的值
  status        text          -- ACTIVE | SUPERSEDED（不物理删除）
  valid_from    timestamptz   -- bi-temporal：生效时间
  valid_to      timestamptz   -- 失效时间（默认 NULL = 当前有效）
  source_ref    jsonb         -- 来源会话/消息 id
  confidence    float         -- 置信度（供后续反馈调参）
  created_at / updated_at     -- 审计
memory_fact_history           -- 每次变更前的完整快照（追加式）
```

> 画像/偏好 = `type IN (PROFILE, PREFERENCE)` 的事实子集；**不单独拆 profile 表**，用 type + 检索限定即可获得 Jarvis profile 的效果。

### 3.3 M3 · PostgreSQL + pgvector 语义记忆

```text
memory_episode
  id            uuid PK
  user_id       text
  kind          text          -- EVENT | STORY | NOTE（会话总结产物）
  content       text          -- 记忆正文（含绝对时间）
  embedding     vector(1536)  -- 维度随模型定（本地/云端 embedding）
  ts            timestamptz   -- 事件/对话时间
  hit_count     int           -- 命中次数
  last_hit_at   timestamptz   -- 最近命中（180 天衰减依据）
  decay_weight  float         -- 检索权重（随未命中时间下降）
  is_l2         bool          -- 敏感标记，仅本地链路可读
  created_at / updated_at
```

- 会话结束的**总结产物**（≈ Generative Agents 的 reflection）写入 M3；原始消息体量过大，不进长期存储，M1 按 TTL 清理。
- 每天一条"每日回顾"NOTE 可选（对应 Jarvis daily.md 的按日期回档能力，但用 kind + ts 检索即可，不单独建表）。

## 4. 写入管线（Write Pipeline · 草案操作）

触发点（三选一并行）：

1. **会话结束总结**（主）：批处理式提炼整段会话 → 产出结构化事实 + 事件笔记。
2. **会话内高价值点**（次）：用户显式"记住这个"/触发规则（决策、个人信息）时实时写入。
3. **每日/定时维护**（异步）：去重合并、衰减、备份。

### 4.1 步骤（核心操作）

| # | 操作 | 输入 → 输出 | 实现要点（粗糙版） |
| :-- | :-- | :-- | :-- |
| 1 | **抽取 Extract** | 对话/事件文本 → 候选记忆（事实/事件/偏好/决策/教训） | 一次 LLM 调用，输出 JSON；要求**绝对时间**，禁止相对时间 |
| 2 | **分类 Classify** | 候选 → `{type, L1/L2}` | type 映射 M2/M3；L2 标记隔离（仅本地 embedding/检索链路） |
| 3 | **规范化 Normalize** | 候选 → canonical form | 统一人称（"我"→用户）、实体、单位、时区、布尔/枚举值 |
| 4 | **查重 Dedup** | 候选 vs 既有 → `ADD / UPDATE / NOOP` | 语义相似度（cosine）> 0.85 视为同主题：正文一致→NOOP；互补→UPDATE 合并；**写侧去重是第一道闸**（Mem0 同款思路） |
| 5 | **冲突解决 Conflict** | 同属性新旧值 → 裁决 | 建议 **bi-temporal（Zep 风格）**：新值 INSERT 并置 ACTIVE，旧值置 SUPERSEDED 且 `valid_to=now`，快照入 history；**不物理覆盖**（比现行"新覆盖旧"更可回滚、可审计） |
| 6 | **写入 Store** | 裁决结果 → M2/M3 | M2：结构化行；M3：正文 + embedding + `last_hit_at` |
| 7 | **注入预备 Stage** | 本轮可注入项 → 候选池 | 供读取管线排序，不直接进 prompt |

### 4.2 定时维护任务（daily/idle）

- **去重合并巡检**：兜底查重，收敛碎片。
- **衰减降权**：180 天未命中 → `decay_weight` 下调（不删除）；可选 MemoryBank 遗忘曲线做更平滑的连续衰减。
- **备份**：每日全量备份（记忆禁止因崩溃丢失）。
- **回档**：daily 级别（按日）与 history 级别（按变更）双保险。

### 4.3 安全闸门

- **写入门控**：L2 候选 → 只允许写入 `is_l2=true` 且 embedding/检索限定本地（Ollama）链路；云端模型永远看不到 L2 明文。
- **注入攻击防护（MINJA）**：外部内容（网页/文档）默认不可直接触发"写入"；写操作需用户参与或显式规则，防止提示注入污染长期记忆。

## 5. 读取与注入（Read / Inject）

1. **查询**：混合检索 = 语义（pgvector top-k）+ 关键词（pg_trgm/FTS）+ 时间/热度加权；M2 事实另走结构化条件（`type + attribute`）。
2. **排序**：相关度 × `decay_weight` × 时间衰减 ×（未来）赞踩权重。
3. **预算注入**：每轮 ≤ 5 条、合计 ≤ 800 token（硬约束，按序截断）。
4. **分域**：L1 记忆进云端对话上下文；L2 记忆只在本地会话注入；命中 L2 时模型侧只给占位提示（"存在本地敏感记忆，已省略"）。
5. 检索失败/空结果：显式降级，不打断主对话。

## 6. 治理规则（相对需求书 §8.2 的建议修订）

| 治理项 | 需求书 §8.2（现行） | 本草案建议 | 状态 |
| :-- | :-- | :-- | :-- |
| 事实冲突 | 新覆盖旧 + 变更历史 | **bi-temporal**：新值生效、旧值失效（SUPERSEDED + valid_to），快照进 history | ⏳ 待确认 |
| 去重合并 | 相似度 > 0.85 自动合并 | 保留阈值；明确写侧合并 + 定时巡检双通道 | ⏳ 待确认 |
| 注入预算 | ≤ 5 条 / ≤ 800 token | 保留（业界共识，硬约束） | ✅ 建议保留 |
| 衰减归档 | 180 天降权（不删除） | 保留；可选遗忘曲线连续化 | ⏳ 待确认 |
| 质量反馈 | 赞/踩调参 | 保留，落地为 confidence/hit 加权 | ⏳ 待确认 |

## 7. 参考对照：Jarvis 系记忆实现（只作参考，不约束实现）

### 7.1 本地 Jarvis（本地工程代码实况）

- **会话层**：Spring AI ChatMemory 抽象；`SummaryChatMemory` 做 token 预算式滚动压缩（超限把旧消息摘要为一条 context），底层 `SQLiteChatMemoryRepository` 把整段消息 JSON 落库为会话 checkpoint（另有 TiDB 版本）。
- **长期/每日/资料层**：MD 语义、DB 行存储——`long-term`（全文一行的 markdown，支持章节 READ/OVERRIDE/APPEND/DELETE）、`daily`（按 `yyyy-MM-dd` 每天一行全文）、`profile`（用户资料全文）；同构还有 soul / agents（人格与规则文件落表）。以 `user_id + scene_id` 隔离。
- **检索**：`memorySearch` = 关键词 contains + 前后文片段截取（**无向量、无排序**）。
- **写入**：由 agent 自主调用工具（Agent-driven），**无抽取/去重/冲突/衰减/反馈管线**；长期记忆全凭 LLM 自律。

### 7.2 企业内 Jarvis 变体（用户口述 v2026）

四层：① 短期上下文 = 数据库 + 内存，单次会话；② 长期记忆 `memory.md` = 数据库表，跨会话持久；③ 每日笔记 `daily.md` = 数据库表，按日期回档；④ 用户资料 `profile.md` = 数据库表，跨会话持久。

> 结论：**企业版与本地工程同源**——本地工程已落地了同一套实现（MD 语义 + DB 表 + scene 隔离 + 会话压缩）。企业版的"三层/四层"描述与代码中的 `memory / daily / profile + soul / agents` 表结构一一对应。

### 7.3 对 OpenAlice 的借鉴与差异

| 维度 | Jarvis（本地/企业） | OpenAlice 目标 | 说明 |
| :-- | :-- | :-- | :-- |
| 短期会话 | DB 整存整取 + 滚动摘要 | Redis + 会话摘要 | 摘要压缩思路可借鉴（MemGPT paging） |
| 长期存储 | MD 全文单行存 DB | M2 结构化事实 + M3 向量记忆 | 我们放弃"全文 markdown 单行"，换取可查询/可版本化 |
| profile | 独立表/独立工具 | M2 的 `type=PROFILE` 子集 | 检索层面等价，结构更统一 |
| 检索 | 关键词 contains | 语义 + 关键词 + 时间混合 | 核心差距 |
| 写入 | LLM 自律 OVERRIDE/APPEND | 显式抽取→分类→去重→冲突→衰减管线 | 核心差距（本草案 §4） |
| 纠错 | 覆盖即丢旧文（无 history） | bi-temporal + history | 更强可回滚 |
| 隔离 | scene_id | user_id + L1/L2 | 我们更强调隐私分域 |
| 文件心智 | MD 即文件（LLM 友好） | 不对外暴露"文件"，走端口 API | 工程上更干净 |

## 8. 分阶段落地路线

| 阶段 | 内容 | 验收 |
