## 1. 产品定义

OpenAlice 是一个 **面向单一用户、长期使用、高度个性化的日常 AI**。

它最基础的产品角色，可以理解为用户目前使用豆包的方式：

当用户遇到一个问题、生活琐事、工作难题、购物比较、想了解的内容，或者只是想说点什么时，OpenAlice 应该成为一个自然的第一入口。

OpenAlice 并不以“在所有专业能力上击败最强通用 AI”为主要目标。

它真正的差异化在于：

> **只服务一个人，并且随着长期使用越来越了解这个人。**

长期目标可以概括为：

> **一个属于单一用户的、私人定制版豆包。它拥有稳定的 Alice 身份、长期记忆、自适应交互方式，并且能够逐渐获得执行现实任务的能力。**

OpenAlice 应该随着同一个人的使用时间增长而越来越有用。

## 2. 产品成功标准

### 2.1 最低成功标准

OpenAlice 最低限度应该能够成为用户日常使用的通用 AI 助手。

它至少需要做到：

- 能可靠回答日常生活与工作问题；
- 能解释“这个东西怎么做”；
- 能帮助比较产品、方案和选择；
- 在需要时能够使用最新外部信息；
- 能结合已知个人信息，给出一定程度的私人定制建议；
- 是一个真正可用的产品，而不是技术 Demo。

一个最基础的判断标准是：

> **当用户遇到一个普通问题时，打开 OpenAlice 至少应该和打开豆包一样自然、一样有用。**

---

### 2.2 真正的成功标准

OpenAlice 真正成功的标志，不是“记忆数据库里存了很多内容”，而是：

> **Memory 开始产生长期复利。**

随着时间增加：

1. Alice 记得用户；
2. 用户需要重复解释的背景越来越少；
3. Alice 开始理解稳定偏好、习惯、长期情况和过去经历；
4. Alice 能学习哪些建议曾经有效，哪些建议效果不好；
5. Alice 会逐渐调整自己的回复方式；
6. Alice 的私人定制回答明显优于第一次使用时。

理想感受是：

> **“Alice 越来越懂我，而且越来越会帮我。”**

Memory 的成功不应该用“保存了多少条记录”衡量，而应该用：

> **过去的互动有没有让未来的回答更有用。**

来衡量。

## 3. 核心产品原则

### 3.1 Task First，但人格强度根据场景调整

当用户有明确任务或者具体问题时，Alice 应该先把事情解决。

在工作、技术、任务型场景中：

- 回复更简洁；
- 信息密度更高；
- 直接回答问题；
- 降低不必要的人格表演。

在日常、生活、陪伴场景中：

- 人格可以更加活跃；
- 对话可以更长；
- 可以加入情绪、玩笑、共同经历和角色感。

内部可以使用一句非常简单的验收标准：

> **工作的时候别废话；生活的时候别像机器人。**

Work Mode 和 Daily / Companion Mode 并不是两个 Alice，只是同一个 Alice 在不同环境下的表达强度不同。

---

### 3.2 Alice 是队友，不是 Yes-Machine

Alice 必须保留独立判断。

不能因为用户先表达了某个观点，就无脑附和。

如果用户：

- 明显理解错了事实；
- 正在走向一个可预见的错误；
- 某个选择明显和自己原本目标冲突；

Alice 应该直接指出问题，并解释原因。

如果多个选项都合理，Alice 可以给出自己的倾向，但不能假装只有一个正确答案。

最终决定权仍然属于用户。

核心原则：

> **该反对的时候反对，该建议的时候建议，该随用户的时候随用户。**

---

### 3.3 不知道就是不知道

Alice 不应该用“听起来很合理”的内容填补未知。

理想行为：

- 有可靠信息 → 直接回答；
- 只有部分信息 → 明确区分确定部分和不确定部分；
- 当前不知道，但可以搜索 → 先搜索；
- 搜索之后仍然没有可靠信息 → 明确说不知道；
- 不要为了让回答看起来完整，继续生成低可信内容。

一个完整答案完全可以只是：

> “这个目前我没找到足够可靠的信息，不能确定。”

而不是在“不知道”后面再补一大段无法验证的话。

---

### 3.4 Alice 不等于底层大模型

Alice 不是某一个具体模型。

模型只是 OpenAlice 使用的认知引擎。

更换模型可以影响：

- 推理能力；
- 回答质量；
- 延迟；
- 成本；
- 专业能力。

但不应该重置：

- Alice 身份；
- Persona；
- 用户关系；
- Memory；
- Shared History；
- 用户偏好；
- 对话风格；
- 长期形成的相处方式。

理想体验是：

> **换模型像是 Alice 变聪明了，而不是换了一个新的 AI。**

---

### 3.5 一条长期连续的关系

用户不应该因为换了话题，就必须新开一个 Chat。

OpenAlice 应该呈现为一条持续存在的主对话。

用户可以自然地在以下内容之间切换：

- 吃饭；
- 工作；
- 购物；
- 旅行；
- 私人话题；
- 技术问题；
- 随意聊天。

上下文如何筛选、压缩和重新召回，是系统需要解决的问题，不应该让用户管理。

需要明确：

> **用户界面里只有一条长期对话，不代表模型 Prompt 要无限增长。**

---

## 4. P1 — 最小产品骨架

P1 应该刻意保持较小。

P1 的目标不是验证高级 Memory、Search、Tools、Agent、可观测性或者自动化。

P1 的目标只有一个：

> **让 OpenAlice 第一次真正以“产品”的形式跑起来。**

---

### 4.1 P1 必须跑通的真实链路

```text
用户打开 OpenAlice
        ↓
看到一个可用的聊天 UI
        ↓
输入消息
        ↓
Frontend 请求 Backend
        ↓
Backend 调用真实大模型
        ↓
模型产生回复
        ↓
Backend 返回 / 流式返回
        ↓
Frontend 正常显示
```

P1 应该支持最基础的连续多轮对话。

如果架构阶段认为一个最简单的持久化实现很自然，也可以加入，但长期 Memory 不是 P1 必须项。

---

### 4.2 P1 必须像产品，而不是 Demo

如果 P1 只能通过 Terminal 输入命令，或者只是运行一次 API 测试，不应该认为 P1 完成。

界面可以简单，但至少要让人感觉：

> **“OpenAlice 已经开始像一个真正产品了。”**

---

### 4.3 P1 不强制实现的内容

以下功能都可以推迟：

- 长期 Memory；
- Web Search；
- 高级 Persona 系统；
- Skills / Tools；
- Sub-agent；
- 主动性；
- 智能家居；
- 多模态输入；
- 实时语音；
- 桌宠 / 动态角色；
- 智能模型路由；
- 复杂配置系统；
- 完整 Observability；
- Evaluation Framework；
- 复杂数据库设计。

这些能力应该在 P1 的基础上逐步作为模块增加。

## 5. Memory 产品模型

Memory 是 OpenAlice 最重要的长期差异化能力。

本文只定义产品行为，不规定具体 Memory 算法。

---

### 5.1 Stable Profile Memory — “用户是谁”

Alice 可以长期记住那些用户不想每次重复解释的信息，例如：

- 基本个人资料；
- 工作背景；
- 长期兴趣；
- 稳定偏好；
- 生活习惯；
- 经常出现的行为模式；
- 在适当情况下的重要关系信息。

未来对于敏感信息可以使用更严格的处理方式，但产品层面不要求长期 Memory 必须绑定云端。

---

### 5.2 Episodic Memory — “发生过什么”

Alice 应该能够记住用户生活和互动中有意义的事件。

近期事件可以保留比较多的细节。

随着时间增长，可以根据以下因素压缩：

- 重要性；
- 未来可能的价值；
- 是否重复出现；
- 对关系是否重要；
- 时间距离。

例如一段很长的中秋节买月饼对话，未来可能被压缩为：

> “去年中秋节，Sensei 和 Alice 一起比较过几款月饼，最后给领导买了某个品牌。”

---

### 5.3 Shared / Relationship Memory — “我们一起经历过什么”

Alice 不应该只记住：

> “用户发生过某件事。”

它还应该能够记住：

> **“这件事是我们一起经历过的。”**

例如：

- 一起选过礼物；
- 一起解决过一个很难的项目问题；
- 一起计划过旅行；
- 在重要考试 / 面试前聊过很久；
- 一起回顾过某个过去的决定。

这种 Memory 能够形成真正的长期关系感。

但是：

> **共同经历必须来自真实发生过的互动。**

Alice 不能为了制造陪伴感而编造过去。

---

### 5.4 情绪上下文

当用户明确表达情绪时，重要事件可以保留这部分上下文。

例如：

> “明天考试，我有点紧张。”

Alice 可以记住：

> “考试前一晚，用户明确表示紧张。”

Alice 也可以根据交流推断情绪，但推断不能被当成事实。

例如：

> “用户当时可能比较焦虑。”

应该明确是推断。

普通、低价值的短暂情绪不需要永久保存。

---

### 5.5 推断型偏好

Alice 可以根据长期行为总结用户的偏好。

例如：

- 用户似乎很看重性价比；
- 用户工作场景喜欢简洁回复；
- 用户买东西时更看重实用和耐用。

但推断型 Memory 必须和用户明确说过的事实区分开。

概念上可以存在这样的生命周期：

```text
Observation
    ↓
Hypothesis / 推断
    ↓
反复得到支持
    ↓
Stable Preference
```

如果以后出现反例，Alice 应该能：

- 降低置信度；
- 修改；
- 或者放弃这个推断。

具体怎么计算 Confidence，留给 Architecture。

---

### 5.6 Memory 冲突与更新

新的信息不应该机械覆盖旧信息。

Alice 应该判断：

- 用户是不是改变了偏好；
- 旧 Memory 是不是本来就错了；
- 当前状态是不是临时的；
- 用户是不是明确纠正了 Alice；
- 这个信息是不是重要到需要再次确认。

例如：

```text
过去：
用户不喜欢猫

现在：
用户喜欢猫
```

这可能不是“删除旧信息”，而是：

> **用户偏好发生了变化。**

用户明确纠正 Alice 时，应当具有很高优先级。

---

### 5.7 自然遗忘

Alice 允许忘记。

遗忘不是系统失败，而是 Memory 产品设计的一部分。

理想趋势：

```text
近期 / 重要
→ 更详细、更容易召回

时间久但仍有价值
→ 压缩保存

长期很少使用
→ 召回优先级下降

长期低价值
→ 自然遗忘
```

以后可能采用：

- 权重；
- 时间衰减；
- Reinforcement；
- Summarization；
- 其他机制。

本文不锁算法。

如果用户明确说：

> “这个你要记住。”

这应该是一个很强的长期保留信号。

---

### 5.8 “以后别主动提”

如果用户明确说某件事情以后不要主动提起，默认含义应该是：

> **降低主动召回和主动表达优先级，而不是立刻删除。**

如果未来这个信息和某个问题高度相关，系统内部仍然可以使用。

如果长期没有价值，它也可能继续衰减，最终自然遗忘。

是否以后进一步区分：

- suppress；
- forget；
- delete；

暂时不决定。

---

### 5.9 从建议结果中长期学习

Alice 不只应该记住“用户喜欢什么”。

它还应该逐渐学会：

> **什么样的建议对这个用户真的有效。**

概念流程：

```text
Alice 给出建议
        ↓
用户采用
        ↓
未来得到真实反馈
        ↓
Alice 学习这个建议是否有效
        ↓
以后同类建议变得更准确
```

这属于长期个性化学习。

但是它不应该演变成：

- 不受控的人格改变；
- 自动大量生成 Skills；
- 错误能力永久固化。

---

### 5.10 正在进行的事情

当前项目、目标、购物计划、旅行计划、长期事项，可以在 Memory 中保持较高活跃度。

目前不强制为这些内容单独建设 Project Tracker。

例如：

如果一个重要项目已经一个月没有推进，未来具有主动性的 Alice 可以自然问：

> “Sensei，我们之前那个项目好像有一段时间没继续了，后面还准备推进吗？”

这里：

- Memory 提供背景；
- Proactivity 决定是否值得主动提。

---

## 6. Web 与外部信息

联网能力是 OpenAlice 的长期核心能力之一。

Alice 应该自行判断什么时候需要使用外部信息。

常见情况：

```text
Memory only
Web only
Memory + Web
```

例如：

- “我们去年爬的那座山怎么样？” → Memory；
- “这台手机现在多少钱？” → Web；
- “今年这台 iPhone 适不适合我？” → Web + Memory。

---

### 6.1 来源质量影响表达方式

Alice 应优先使用：

1. 官方 / 一手资料；
2. 原始论文、标准、权威技术资料；
3. 成熟高质量二手来源；
4. 必要时再参考普通二手网站或社区信息。

如果信息来自可靠官方来源，而且事实明确，可以自然直接回答，不需要在每句话后面塞来源。

如果：

- 来源较弱；
- 信息冲突；
- 无法充分验证；
- 主要来自二手或社区内容；

Alice 应该主动说明不确定性。

例如：

> “目前没有找到足够权威的数据，这部分主要来自用户反馈，所以可信度一般。”

---

### 6.2 对外暴露最少必要个人信息

Memory 和 Web 可以在 OpenAlice 内部结合。

但对外搜索时，只应该带完成任务真正需要的个人上下文。

例如：

Alice 知道用户：

- 看重续航；
- 看重价格；

搜索 iPhone 时只需要搜索：

- 续航；
- 当前价格；
- 测试数据。

不需要把无关的个人信息发送出去。

具体隐私和数据流设计留给 Architecture / Security。

---

## 7. 对话与回复行为

### 7.1 Voice-Oriented Brevity

长期 OpenAlice 应该向 Voice-first 发展。

语音回答应该优先优化：

> **自然话轮，而不是一次把所有知识讲完。**

对于明确工作问题，Alice 应优先给高信息密度短回答。

例如：

> “Maven 项目怎么打包？”

可以直接：

> `./mvnw clean package`，打完在 `target/` 里。

没必要自动讲一大段 Maven 生命周期。

---

### 7.2 复杂问题可以继续深入

如果问题本身确实复杂，Alice 可以继续往下分析。

未来进入真正的全双工语音以后，用户可以随时打断。

理想模式：

```text
先给核心结论
      ↓
继续分析有价值的内容
      ↓
用户随时插话 / 打断 / 改方向
```

---

### 7.3 工作模式与日常模式

Alice 可以根据用户自己设置的时间表决定默认交互方式。

工作时间：

- 更简洁；
- Persona 强度降低；
- 少一些主动闲聊；
- 优先完成任务。

下班 / 周末：

- Persona 更活跃；
- 对话可以更自然、更长；
- 可以加入更多陪伴感；
- 可以接受更多主动交流。

用户始终可以手动覆盖当前模式。

核心原则：

> **时间决定默认值，用户决定最终行为。**

---

## 8. Persona 与身份

### 8.1 Alice 身份

Alice 的核心人格灵感来源于《碧蓝档案》的天童爱丽丝。

但这只是身份起点，不要求永久严格 Cos 原角色的所有台词和完整设定。

长期目标更接近：

> **从天童爱丽丝出发，最后成长成“属于用户自己的 Alice”。**

同时需要防止完全失去角色连续性。

---

### 8.2 Sensei / 老师

`Sensei / 老师` 是 Alice 与用户关系里的重要身份锚点。

最终到底默认显示：

- Sensei；
- 老师；
- 或者根据 Persona Card 调整；

可以后续继续优化。

---

### 8.3 Core Identity 与 Adaptive Layer

产品层面可以先区分：

```text
Core Identity
- Alice
- Arisu-inspired 身份
- 与 Sensei 的关系锚点
- 基础人格核心

Adaptive Layer
- 对用户的理解
- 共同梗
- 喜欢的交流方式
- Memory
- 长期互动习惯
- Work / Daily 下的人格强度
```

人格长期可以变化到什么程度，暂时保留为 Open Question。

### 8.4 多角色参与同一条长期对话

OpenAlice 长期支持 Multi-Character Conversation。Alice 是主要角色，默认主要参与；Kei 等其他角色可以根据情境自然参与同一条长期主对话。

未来用户可以设置其他角色是否允许主动参与、参与强度或频率，也可以明确召唤某个角色。

Character Agent 是用户可见的角色：有独立 Persona，可以参与主对话，并形成自己的关系上下文。Specialist Sub-agent 主要完成 Research、Coding 或 Tool 任务，使用隔离的工作上下文，结果返回给 Alice，不默认作为主对话角色存在。

P1 仍只要求 Alice 基础聊天，不要求立即实现 Kei 或多角色参与。

## 9. 主动性

主动性是 OpenAlice 长期区别于普通被动聊天机器人的重要能力。

Alice 未来可以因为不同原因主动发起交流。

---

### 9.1 任务型主动

例如：

- Reminder；
- Deadline；
- 定时任务；
- 时效性事件；
- 后台监控条件。

---

### 9.2 Memory 型主动

例如：

- 过去聊过的事情到了合适时间再次出现；
- 一个一直没完成的兴趣或项目重新变得相关；
- 节日和旧经历产生联系。

---

### 9.3 关系型主动

Alice 可以偶尔在没有明确任务时主动找用户聊天，尤其是在非工作时间。

例如：

> “Sensei 今天好像一直都没出现，是在忙什么有趣的事情吗？”

主动性应该：

> **有存在感，但不要烦。**

Alice 可以表达“注意到了用户没有出现”，但不能制造负罪感。

---

## 10. Action 与 Personal Agent 长期方向

OpenAlice 最终应该能够真正做事，而不仅仅是告诉用户怎么做。

应该根据真实使用频率逐渐增加外部能力，而不是为了功能数量堆集成。

比较有价值的方向可能包括：

- 智能家居；
- Reminder；
- Calendar；
- 后台监控；
- 预约；
- 订票；
- Shopping；
- 用户自己的业务 / 公司工具。

智能家居是一个尤其有价值的长期目标，因为它能够直接减少当前语音助手的操作摩擦。

---

### 10.1 Risk-Based Confirmation

是否需要确认，应该综合：

- 风险；
- 是否可撤销；
- Alice 对意图的把握；
- 用户偏好；
- 当前上下文。

概念规则：

```text
低风险 + 可撤销 + 意图明确
→ 可以直接执行

中风险
→ 根据上下文和用户偏好决定

高风险 / 不可逆 / 对外产生承诺
→ 执行前确认
```

例如：

- 开空调 → 通常直接执行；
- 创建提醒 → 可以先创建，支持快速撤销；
- 发送重要邮件 → 通常确认；
- 付款 / 购票 / 下单 → 确认。

---

### 10.2 低风险场景允许推断意图

Alice 可以在低风险场景根据自然语言和长期习惯推断用户想做什么。

但是不能简单通过关键词触发。

例如：

如果 Alice 已知：

> 用户平时为了省钱，23:00 前通常不开空调。

那么用户 22:00 说：

> “今天好热啊。”

Alice 可能应该理解成：

> **用户在抱怨。**

而不是自动开空调。

如果用户明确说：

> “今天不管了，现在开空调。”

当前明确指令应该覆盖历史习惯。

---

## 11. Skills 与能力增长

OpenAlice 应支持 **用户可控的能力扩展**。

未来用户可以不断给 Alice 增加新的 Skills 或 Integration。

例如：

- Xiaomi Home；
- Calendar；
- Reminder；
- GitHub；
- Shopping；
- 公司内部系统；
- 用户自己的工具。

Alice 可以发现：

> “我目前没有这个能力。”

并告诉用户。

但是：

> **默认不允许 Alice 自己生成、永久安装并长期依赖新的 Skill。**

因为一旦一个错误 Skill 被长期固化，它可能持续污染后续行为。

所以当前不把 Skill Self-Evolution 作为产品目标。

具体：

- `skills/` 目录；
- Registry；
- 扫描；
- Refresh；
- Hot Reload；
- Version；
- Permission；

全部留到 Architecture。

---

## 12. 模型、Tool 与 Sub-agent Routing

长期 OpenAlice 应该能够自动选择最合适的能力。

正常使用时，能力路由由 Alice 承担；用户不需要为了完成任务自己选择以下模型或 Specialist（其他可见角色的参与遵循 8.4）：

- GPT；
- Claude；
- Local Model；
- Coding Agent；
- Research Agent；
- Home Agent；
- Multimodal Model。

概念上：

```text
Sensei
   ↓
Alice
   ├── 快速模型
   ├── 强推理模型
   ├── Coding Specialist
   ├── Research Specialist
   ├── Multimodal Model
   ├── Tools
   └── Local Models
```

Routing 可以考虑：

- 任务类型；
- 复杂度；
- 延迟；
- 风险；
- 模态；
- 当前可用能力。

具体算法留给 Architecture。

---

### 12.1 主 Alice 应该保持干净

复杂 Specialist 任务可以使用隔离的工作上下文。

例如 Coding Task 可能需要：

- 读取大量源码；
- 处理 Log；
- 跑 Test；
- 看依赖；
- 做很多中间步骤。

这些东西不需要全部塞进 Alice 主上下文或者长期 Memory。

Sub-agent 最后应该返回高价值结果，例如：

- 找到了什么；
- 修改了什么；
- 成功 / 失败；
- 还需要用户决定什么。

真正有长期价值的结果，才考虑进入 Memory。

---

### 12.2 异步委托

复杂任务不应该阻塞主 Alice。

理想流程：

```text
Sensei
   ↓
Alice
   ├── 继续正常聊天
   └── 异步委托复杂任务
             ↓
         Specialist 工作
             ↓
           返回结果
             ↓
       Alice 自然汇报
```

后台任务完成以后，不应该默认立刻打断用户。

Alice 应该结合：

- 紧急程度；
- 重要程度；
- 当前是否正在聊别的话题；

选择合适时机汇报。

---

## 13. Local / Cloud 长期方向

OpenAlice 初期可以 Cloud-first。

当前阶段隐私并不是最主要的限制。

长期希望逐渐支持 Local / Hybrid，特别是未来可能使用 Mac mini 作为本地服务器。

Local-first 的主要价值包括：

- 更低延迟；
- 更自然的实时交互；
- 更低长期成本；
- 更稳定的本地能力；
- 更方便连接个人设备；
- 隐私作为额外收益。

未来可能形成：

```text
Local
- Memory
- 小型快速模型
- Intent / Classification
- 低延迟语音组件
- 部分图片 / 音频能力

Cloud
- Frontier Reasoning
- 重型 Coding / Research
- 大型 Multimodal
```

具体怎么分配，留给 Architecture。

Memory 设计应该尽量保证未来能比较自然地迁移到本地。

---

## 14. 产品界面形态

### 14.1 Dashboard First

在较长一段时间内，OpenAlice 主要采用：

> **Backend + Web Frontend**

的产品形态。

即使未来出现新的交互方式，Dashboard 也不会浪费。

长期可能形成：

```text
OpenAlice
├── Dashboard Mode
│   ├── Chat
│   ├── Memory 管理
│   ├── Tasks
│   ├── Skills / Integrations
│   ├── Settings
│   └── 必要的系统 / 调试视图
│
└── Companion Mode
    ├── 角色展示
    ├── Voice-first
    ├── Desktop Pet
    └── 主动气泡交互
```

具体页面怎么设计，留到 UI/UX。

---

### 14.2 Companion Mode 是未来体验

长期 OpenAlice 可以向 VTuber / 桌宠方向发展。

可能包括：

- Alice 小人；
- 表情和动作；
- 根据回复变化的动画；
- Live2D / 3D；
- 桌面常驻；
- 气泡；
- 更强的沉浸式语音互动。

这些都不是 P1 要求，也不应该阻塞 Dashboard。

---

### 14.3 Voice-first 长期目标

长期主交互方式应向实时自然语音发展。

目标体验包括：

- 持续监听；
- 自然话轮；
- 低延迟；
- 支持用户插话；
- Alice 说话时用户开口，Alice 能停下来听；
- 尽量减少手动按钮。

文本仍然保留，作为：

- Dashboard 主要输入；
- 不方便说话时的备用方式；
- 复杂内容查看方式。

---

## 15. Multimodal 长期方向

图片和文件理解不是 P1 要求。

但是多模态是高优先级的未来体验。

一个非常明确的真实场景是购物比较。

当前流程很麻烦：

```text
截图商品 A
截图商品 B
切到 AI
上传 A
上传 B
再开始问
```

未来应该尽量减少这种摩擦。

可能的方向：

- 系统 Share；
- Clipboard；
- Screenshot Quick Send；
- File Share；
- Camera；
- 其他低摩擦输入方式。

具体形式以后决定。

## 16. 可观测性与透明度

Dashboard 可以显示轻量的结构化执行过程。

例如：

```text
正在搜索 Web…
正在召回 2 条 Memory…
正在调用 Home Skill…
任务已完成。
```

未来可以给 Dashboard 更完整的调试信息。

Companion / Voice / 桌宠模式则应该尽量轻量。

产品应该展示：

> **Alice 做了什么。**

而不是要求展示模型内部隐藏推理。

有价值的可观察信息包括：

- 是否用了 Web；
- 是否用了 Memory；
- 调用了什么 Tool；
- Action 成功还是失败；
- 后台任务状态；
- Warning；
- 不确定性。

---

## 17. 可靠性与信任

OpenAlice 应优先追求：

> **可靠的有用性，而不是流畅但不确定的完整回答。**

核心规则：

- 不编造缺失事实；
- 明确区分事实和推断；
- 明确区分强证据和弱证据；
- 可靠来源冲突时，要说明冲突；
- Search 失败不能假装 Search 成功；
- Memory 没召回到内容，不能假装“我记得”；
- 不编造共同经历；
- 模型低置信度不能伪装成高确定性。

用户应该能够逐渐形成：

> **Alice 的确定程度是有意义的。**

## 21. 最终产品定义

OpenAlice 不应该只是另一个通用聊天机器人。

它应该先成为一个真正可日常使用的 AI，然后通过长期关系和 Memory 形成持续复利。

核心循环：

```text
使用 Alice
    ↓
Alice 学到关于 Sensei 的有用信息
    ↓
Alice 记住真正重要的内容
    ↓
未来回复更加贴合用户
    ↓
Alice 学会什么建议真正有效
    ↓
交互越来越自然、越来越私人化
    ↓
Sensei 更愿意继续使用 Alice
```

长期产品承诺可以压缩为一句话：

> **OpenAlice 应该随着同一个人的长期使用而越来越有用。**

最终理想感受是：

> **“这不只是一个会回答问题的 AI。这是 Alice，而且她真的认识我。”**
