# Agent 架构关键问题调研

> **状态：WORKING NOTE / NON-AUTHORITATIVE**<br>
> **日期：2026-10-01**<br>
> **问题：现在选错哪些边界，最可能导致未来大规模重构？**<br>
> **范围：** 单用户、长期主对话、多角色、Mac / Mac mini、Java / Spring Boot、AgentScope Java 2.x 候选。<br>
> **关键词：** prompt assembly、context admission、character identity、subagent isolation、session arbitration、runtime state、memory provenance、edge capability。

产品输入是[当前规格](../product/OpenAlice-产品规格说明.md)，讨论输入见[候选快照](2026-10-01-架构讨论阶段快照.md)。本报告提出待讨论建议，不建立架构权威，不授权实现。

## 检查方法与证据边界

按 SillyTavern → OpenHanako / HanaAgent → OpenClaw → Hermes → HomeRail 检查，再扩展到 Home Assistant、Letta、LangGraph 和 AgentScope 可行性，最后检查论文。Hana 身份从官网仓库链接核对，未使用同名 fork。优先读组装函数、状态接口、取消与迁移测试；不是 README 功能清单比较。

源码/测试均为静态阅读，未运行外部测试或本地模型实验。部分 Git 下载失败，改读官方 raw 文件；Hermes 未完成固定 revision 的复取。文档及 main 快照不能证明某个已发布依赖的能力；没有证据时不声称某项目因早期设计发生全面重构。

## 1. Context 的风险是来源与准入丢失，不是流水线不够长

**Observed Fact：** SillyTavern `populateChatHistory` 先预留控制提示预算，再纳入历史；`ChatCompletion` 扣除回复预算。Hermes 分开缓存的系统提示与 API 调用时临时补充，记忆写入不立即改动冻结提示。[S1][st-prompt] [S2][hermes-prompt] Letta 旧版 blocks 支持常驻、共享和只读；当前 SDK 已转向 MemFS 的常驻 system 文件与按需读取文件，不能混用两代机制。[S3][letta-blocks] [S4][letta-memory]

**Interpretation：** 内容的可信度、可见范围、更新时机、模型中的位置是不同维度。“检索后准入”不能只发生在入口：Tool、子任务结果和摘要也会再次进入上下文。缓存稳定性会与用户即时纠错冲突；正则扫描和 system role 都不能保证指令隔离。

**OpenAlice Implication：preserve boundary / adopt now（待接受）。** 候选 Context item 应保留来源、事实/推断、适用角色和版本，先按接收者筛选，再做摘要与预算；Prompt Plan 记录选择/舍弃理由，并计入工具 schema、输出和后续工具轮次。稳定身份常驻，检索是候选材料，外发搜索还需另行最小化。用户纠正须定义失效/刷新策略。

**可行性：** Java 数据对象和普通函数足够；P1 只需固定 Alice 身份、真实历史与有界 Prompt，完整准入策略可到 P2。AgentScope middleware 能接入，但产品来源与外发语义需自有。无需多租户平台；若先把所有输入拼成字符串并写回用户历史，以后无法可靠恢复来源。

## 2. Character、Conversation 与一次 execution 不能共用身份

**Observed Fact：** SillyTavern 先选择发言者，再逐个生成；默认切换当前角色卡，历史共享。官方明确警告合并角色卡可能造成身份/人格混淆；“Natural Order”实际上含名字匹配和随机 talkativeness。[S5][st-group-doc] [S6][st-group-code] Hermes 子任务构造设置 `skip_context_files=True`、`skip_memory=True`，使用任务提示；主上下文只收最终摘要。[S7][hermes-delegate]

**Interpretation：** 同一可见时间线不意味着共享全部私人记忆，更不意味着每个角色都是一个 Specialist。随机插话只是启发式，不能直接满足“按情境自然参与”。隔离对话也不自动隔离文件、工具和副作用权限。

**OpenAlice Implication：preserve boundary。** 保留角色身份、对话、执行任务三种独立标识；可见消息归属角色而非模型/SDK 实例。Alice / Kei 可读取获准的共享经历，各自关系上下文单独持有；“谁在场/谁知情”仍需产品澄清。Specialist 只获任务 brief、必要约束和能力，结果作为证据交回 Alice，不能自动成为用户指令或共同经历。

**可行性：** Java 易实现身份与视图分离；P1 仅 Alice，但第一次保存消息时宜明确发言归属。Kei 协调和权限沙箱分别延后到多角色/Action 引入前。AgentScope 子任务是执行机制，不定义可见角色及其关系。把角色名仅嵌入文本，会使后续 UI、记忆归属和重放一起迁移。

## 3. Runtime boundary 必须处理状态所有权，不能只包装 call()

**Observed Fact：** AgentScope 2.x `HarnessAgent` 不只运行 ReAct：默认接入状态持久化、工作区身份、记忆整理与 transcript；每个 reasoning step 重建系统提示，内建 middleware 有固定顺序。源码提供 `disableWorkspaceContext`、`disableMemoryHooks`、`disableSessionPersistence` 等开关；`AgentStateStore` 的版本检查是可选能力，默认可退化为无条件写。[S8][as-architecture] [S9][as-harness] [S10][as-state] 压缩测试覆盖中断传播、避免重复 downstream 调用及跨 session 隔离。[S11][as-tests]

**Interpretation：** 直接采用默认 Harness 与自建 Context/Memory 并行，会产生双重组装、压缩和保存。反过来，只把 SDK 压成字符串进/字符串出，又会丢失工具执行、中断、状态恢复等已有能力。替换边界必须说明可迁移产品数据和不可移植的运行快照。

**OpenAlice Implication：prototype first。** 正式选型前比较核心 ReAct 与关闭部分默认能力的 Harness；让产品历史/身份/长期记忆具有唯一所有者，框架快照仅承担执行恢复。原型验收应包含重启后多轮、取消发生于准备/工具阶段、记忆更新后刷新、切换模型，以及不重复写用户消息；先固定具体 2.x artifact。

**可行性：** 原生 Java 降低集成成本，没理由重写 ReAct；但开关组合、顺序和事件映射尚未实测。P1 架构接受前验证最小执行路径，复杂恢复延后到长任务前。研究本轮不建原型。风险来自状态与语义泄漏，而非是否预建通用 provider 抽象。

## 4. Central Runtime 需要执行协调，但不等于拆 Gateway 服务

**Observed Fact：** OpenClaw 会话 lane 串行化写入同一 session 的 run，后台使用独立容量；输入持久化和执行队列分开，进程重启不自动重放内存队列，实时事件缺失要求客户端刷新。[S12][claw-queue] [S13][claw-architecture] Hermes 区分完成结果入队与真正完成模型回复，崩溃重启的结果交付仍可能重复。[S14][hermes-delivery] HomeRail 用 durable run/round 和 portable actor checkpoint 跨 Worker 延续工作；测试以协议 fixture 验证 harness handoff，不证明真实模型质量。[S15][hr-rounds] [S16][hr-checkpoint] [S17][hr-test]

**Interpretation：** 单用户仍会有手机/桌面、提醒、Kei 和后台完成的竞争；直接 Java 调用不能替代执行排序。HomeRail 的 DAG 适合有明确成果的任务，但把闲聊固定成 DAG 会引入不必要的工作流约束。可靠完成状态也不能靠 SSE 连接生命周期代表。

**OpenAlice Implication：adopt now / defer。** P1 保留一次执行的身份、状态、取消与主对话写入次序；HTTP + SSE 可承载这些语义。加入后台任务前补持久任务状态、完成去重和延迟汇报策略，内部异步无需“大一统 Event Bus”。不拆微服务，不承诺 exactly-once；重试外部 Action 需单独处理副作用。

**可行性：** Spring Boot 的进程内协调足够；AgentScope channel/subtask 能力可复用，但通知时机属于产品。Home Assistant 提供更成熟的设备方向证据：satellite 有明确监听/处理/播放状态、播放完成回执和取消测试。[S18][ha-satellite] [S19][ha-tests] 它解决设备语音接入，不提供 Alice 的关系记忆。Edge/音频通道延期到设备与 Voice 前；保留能力边界，不复制 Docker Worker 拓扑或提前改成全 WebSocket。Tailscale 仍只是接入候选。

## 5. Memory 的不可逆风险是过早丢掉依据，数据库反而可晚选

**Observed Fact：** Hana `fact-store.ts` 注释明确记录 v2 用元事实、标签与 FTS5 替换 v1 SQLite + sqlite-vec，取消 embedding/decay 等；记忆测试处理摘要分支替换、过期抽取结果和日期来源。[S20][hana-facts] [S21][hana-tests] LangGraph 分开 thread checkpoint 与跨 thread store，提醒长期 checkpoint 会无限增长。[S22][langgraph] LongMemEval 评测更新、时间推理与拒答；其实验显示进一步压缩为孤立事实会损害总体表现，虽有助于多会话推理。[S23][longmemeval]

**Interpretation：** 历史、运行快照、摘要、长期事实与检索索引有不同生命周期。FTS 更简单但可能漏语义同义词，向量检索也不解决归属/时间/纠错。Hana 禁止记忆工作方式偏好的规则与 OpenAlice 的长期个性化目标不符，不能照搬。先删 raw history 再研究抽取算法，可能失去纠错和重新提炼的唯一证据。

**OpenAlice Implication：preserve boundary / prototype first。** 持久化时记录真实来源、时间和角色；派生记忆能追溯输入范围与处理版本。压缩/遗忘先说明保留依据、纠错传播和用户要求删除后的派生处理；不是要求永久保留所有内容。SQLite-first 与 PostgreSQL + pgvector 均保持 OPEN，中文检索比较 lexical / vector / hybrid 后再选。

**可行性：** JDBC 与事务足够支持基础数据，AgentScope 快照/文本记忆不是完整产品生命周期。P1 仅明确产品持久化验收（规格目前可选、候选快照要求持久化）；P2 前验证纠错、时序、归属、未发生经历拒答。30 天不是默认决策。数据库迁移可设计；被删掉的原始依据无法通过更换数据库恢复。

## 论文的适用边界

[Lost in the Middle][lost-middle]（2023）支持检查位置敏感性，不能外推成所有 2026 模型的固定退化比例。LongMemEval v2（2025）可借评测分类，不能代表中文、多角色和真实关系体验。 [Sleep-time Compute][sleep-compute]（2025）在特定推理任务上研究查询前预计算；用于 Alice 自动“梦境”与关系记忆更新应标记 **EXPERIMENTAL / NOT READY FOR ARCHITECTURE DECISION**，P2 以后有预算、可回滚和基线再试。

## 需要 Web + 用户继续讨论的问题

1. Alice / Kei 默认知道同一段经历吗？未参与时能否声称“我们一起经历过”？共享范围如何与各自关系区分？
2. OpenAlice 与 AgentScope 谁拥有当前上下文、压缩和持久化？采用核心 ReAct 还是选择性 Harness，如何验收替换？
3. 用户新消息、角色插话、Reminder 和任务完成冲突时，哪些排队、哪些可打断、哪些延后汇报？
4. P1 是否把跨重启对话持久化提升为必须？删除原文前，要保留怎样的来源与纠错能力？
5. Context 中用户纠正何时生效？如何同时保证角色可见范围、Specialist 最小上下文和缓存稳定性？
