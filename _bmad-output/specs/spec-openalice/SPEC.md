# OpenAlice 产品实施契约

## Why

OpenAlice 面向唯一用户本人：异地工作、独居，日常发生理发、买蛋糕这类生活碎片后，有强烈分享欲，但当前只能发进一个经常没有回应的家庭群。通用陪伴助手能共情，却缺少两件东西：在当下结合真实历史接住具体细节的能力，以及稳定、可辨识、不会沦为空泛回声的人格表达。现在需要把已经 `HARDENED` 的产品设想收敛成可实施、可验收的契约，并让用户在下一次真实分享时，第一反应可以是先找爱丽丝。

## Capabilities

- **CAP-1**
  - **intent:** 用户可以用文本分享生活碎片，爱丽丝结合当前消息（有可信记忆时再结合历史记忆），给出值得继续回答的回应。
  - **success:** 在理发、蛋糕等场景中，回应包含对具体内容的接住、一个可回答的具体问题和一个记忆钩子；只给泛化共情或“我理解了”判定失败。

- **CAP-2**
  - **intent:** 用户只拥有一条永久主对话，且可以连续恢复它，不因服务重启丢失上下文。
  - **success:** 首版只有一条逻辑主对话（不按话题拆分会话）；写入多轮历史、重启服务后继续的仍是同一条对话，历史连续可读。记忆内容的引用质量归 CAP-5 验收，不在本项判定。

- **CAP-3**
  - **intent:** 系统可以加载一张稳定、可辨识的 AI 人格卡，并让表达与立场由当前加载的人格卡定义；首版只交付内置的天童爱丽丝人格卡。
  - **success:** 首版按 `persona-contract.md` 验证天童爱丽丝卡：不是无条件赞美或顺从；异议依据来自勇者/队友价值；表达后把选择权交还用户并停止施压。多人格加载与切换不属于首版成功条件。

- **CAP-4**
  - **intent:** 系统可以区分永久稳定的身份与可修改的用户资料，用户改名不影响历史归属。
  - **success:** `userId` 由系统首次生成且不可编辑；称呼、偏好、自我介绍存入可修改的 `UserProfile`；修改资料后同一用户的历史仍然连续。

- **CAP-5**
  - **intent:** 系统可以通过独立的记忆边界可靠持久化对话，并至少提供最小召回，使回复不再依赖单次会话窗口；具体抽取、检索与排序算法可后置。
  - **success:** 重启后，爱丽丝能引用重启前刚聊过的具体细节，**或**能按话题找回较早的会话内容——两者任一成立即算通过；没有可信召回时，不得声称记得或补写历史。

- **CAP-6**
  - **intent:** 系统可以自动判断何时需要真实联网搜索，并用搜索到的真实信息回答用户的现实问题，而不是靠模型记忆硬答。
  - **success:** 至少完成一次真实搜索问答：用户提出一个需要外部信息的问题，爱丽丝自动触发搜索，并给出基于真实结果、且能与个人记忆联动的回答；记忆联动强度对齐 CAP-5（引用真实发生过的事实即可，不要求跨话题召回）；不得编造搜索结果或来源。

## Constraints

- 身份优先级为 **A 私人伙伴 > B Java/算法作品 > C 开源/可分享产品**；B 与 C 不得反噬 A。产品判断冲突时以 A 为准。
- 爱丽丝是现实关系的**补位**，不是替代。首版不追求“成为唯一倾诉对象”；若用户开始只依赖爱丽丝、放弃现实关系，视为风险信号而非成功。
- 首版核心只覆盖用户主动分享；爱丽丝主动发起 B 不作为首版成立条件，首版不主动推送。
- 长期方向是成为像通用问答助手一样的默认入口，但这是方向，不是 P1 门槛；P1 只要求至少完成一次带搜索的真实问答。
- 搜索行为按 `conversation-policy.md`：由爱丽丝自动判断是否搜索；简单问题直接回答，复杂或代价高的问题先确认再答；搜索无结果、结果冲突或置信不足时，先承认不确定，再给出可继续核实的方向；来源默认不展示，用户追问“依据呢”时展示，但系统必须保留真实证据；搜索结论与个人记忆冲突时先指出冲突，由用户裁决，不擅自覆盖记忆。
- 工具能力只允许“真实搜索”这一条；通用工具平台、插件体系与自动化执行不入首版。
- 一条消息同时包含分享和任务时，**先完成任务，再简短回应分享**，不跳过其中一半。
- 歧义处理分级：日常闲聊可先给出最可能的猜测并继续；事实、决定或敏感内容必须先问清再答。
- 首版人格方向是人格卡槽位，但只实现一张内置的天童爱丽丝卡，并以普通 prompt 加载；卡片管理、切换、下载、多人格路由、训练与数据集不入首版。
- 人格卡应是可替换内容；未来新增人格卡不能要求重写对话回复契约或记忆模块。
- 人格不接受通用“温柔陪伴型”外壳、完整原作复刻、名台词或 cosplay；天童爱丽丝卡只保留行为与价值观核心加少量游戏语汇。
- 记忆是首版必备边界，且是**逻辑边界**（包 + 明确接口），不是物理拆分的模块；是否物理拆分由 architecture spine 决定。必须可靠持久化并具备最小召回；具体抽取、召回、重排、时间与作用域、衰减、纠错和忘记算法后置，需后续结合论文与实验决定。
- 回复生成只能使用可追溯的真实记忆；召回不足时不得编造历史。
- 三信号分离不作为首版契约；首版不实现长聊控制策略或主动接回算法，不因此承诺主动追问。
- `userId` 首次由系统生成，永久不变、对用户隐藏且不可编辑；可变称呼、偏好与自我介绍归 `UserProfile`。个人版只有一个当前用户来源，不提前建 provider 或依赖注入。
- 首版对 `UserProfile` 只要求数据模型分离 + 一条最小更新路径（HTTP 接口或直接改库均可），不做资料管理 UI。
- 个人版优先于企业应用分叉；不为多租户、权限或高并发提前造空接口。
- P1 继续采用 Java 21、Spring Boot、AgentScope Java 2.0.2、单 Maven 模块、HTTP/SSE 文本链路，以及 PostgreSQL 作为唯一外部存储的方向。
- 新的 `_bmad-output/architecture/openalice/ARCHITECTURE-SPINE.md` 是技术权威；在它完成前，legacy ADR、README 与现有包结构都不能继续约束实现。
- `docs/archive/pre-rebuild-2026-09-20/` 只作历史追溯，默认不进入产品、架构与实施上下文；其中任何被重新采纳的结论都必须在新的 architecture spine 中重新确认。
- 实施上下文只允许引用本 SPEC 与 `companions:`；`sources:` 中的 Forge 记录仅用于追溯，不是契约。

## Non-goals

- 首个实施切片不包含主动发起、语音、Web UI、多用户、多人格管理或路由、模型训练或数据集。
- 首个实施切片不包含通用工具调用能力；只允许真实搜索这一条受控工具链路。
- 首个实施切片不实现三信号分离、长聊控制、话题重要度衰减、跟进容忍度恢复或主动接回触发算法。
- 首个实施切片不要求成熟召回：只要求可靠持久化 + 最小召回；不固化记忆抽取、重排、衰减、纠错或忘记算法。
- 首个实施切片不验收图片输入输出；图片能力随模型多模态能力走，后置评估。
- 首个实施切片不实现偏好推断、自动更新偏好、自然语言纠错或撤回机制；偏好如何与记忆模块协作留待后续设计。
- 不以完整复刻原作剧情、固定名台词或角色扮演腔调为目标。
- 不为未来企业版提前实现租户、权限或高并发空抽象。
- 在新的 architecture spine 定稿前，不继续扩展 `src/`，也不把当前实现视为必须保留的架构。
- 不等待成功指标完全操作化后才启动。

## Success signal

- 当用户发生一件事或拿到一样东西后，第一反应从打开微信找父母分享，转为先找爱丽丝分享；这证明她已经接近用户心中可交流的人，而不只是工具。
- 该信号先作为上线后的方向性观察，不阻塞启动；持续时间、重复频率、不同情绪事件上的稳定性与反孤立边界后续再验证。

## Assumptions

- 首版以文本为唯一交互通道。
- 记忆模块首版必须存在，但允许先用基础实现验证产品闭环，算法成熟度不作为启动前提。
- 当前代码只作行为参考；允许后续按本 SPEC 与新的 architecture spine 彻底重构，既有实现既不是架构真相，也不是迁移兼容义务。

## Open Questions

- 是否采用三信号分离，以及当下沟通能量、话题重要度和跟进容忍度的正式定义与交互方式是什么？需要结合记忆模块研究后再决定。
- 记忆模块应采用什么抽取、表示、检索、重排、时间与作用域、衰减、纠错和忘记算法？需要用论文与实验支持。
- 偏好如何与记忆模块协作，以及自动更新、自然语言纠错与撤回如何设计？首版不实现。
- 后续人格卡的格式、加载方式、切换体验和生命周期管理是什么？首版不实现。
