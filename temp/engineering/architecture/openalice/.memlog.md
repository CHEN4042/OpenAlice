- (constraint) 个人版唯一用户；不为多租户、权限、高并发提前造 provider、DI 或空抽象。
- (constraint) 首版只做文本主动分享链路；主动发起、语音、Web UI、工具调用、多用户、多人格、训练与数据集不在首个切片。
- (constraint) SPEC 当前约束技术方向为 Java 21、Spring Boot、AgentScope Java 2.0.2、单 Maven 模块、HTTP/SSE 与 PostgreSQL；若架构结论要改变，必须先回写 SPEC。
- (constraint) 现有 src 与归档 ADR 只作行为参考，不继承其接口、包结构或兼容义务；新代码按本 spine 重建。
- (direction) 默认走 Coaching path，先锁定范式、边界、状态所有权和首个垂直切片，再进入 story/build。
- (question) 本次 architecture 只交付 build substrate spine，还是还需要一份面向用户阅读的架构说明？
- (question) OpenAlice 的核心运行范式应采用哪种：单体分层、端口/适配器（hexagonal），还是以对话回合/事件为轴的 pipeline？
- (direction) 用户确认进入 Coaching path；本次默认只交付 ARCHITECTURE-SPINE.md，白话解释留在会话中，额外人类可读架构说明待定。
- (constraint) 首要工程约束是修改局部化：新增或调整一个功能时，不能牵动大量无关模块；功能点应可快速定位，调用链清晰且依赖方向明确。可配置项和可变数据应通过持久化承载，避免硬编码。该约束优先于框架形式上的纯粹性。
- (constraint) 人格与记忆算法是高频变化区，必须拥有独立模块和稳定接入边界；算法模块的进化、替换或局部失败不得迫使核心对话业务代码同步修改。这里是真实的第二实现来源，允许存在必要抽象，但不提前泛化其他模块。业务模块承担 Java 工程能力、工具与技能的演进；算法模块承担 Java 算法实验与增强。
- (direction) 优先形成“核心对话业务 -> 算法端口 <- 可替换算法实现”的依赖方向；接口形状由当前真实输入输出驱动，不建立预测性空接口。
- (question) 算法模块的职责边界尚未确认：需要向用户说明“业务大脑负责一轮对话流程，算法副脑提供记忆检索、重要度、沟通意愿与跟进权限等结构化建议；用户始终只看到一个 Alice，算法不得另行生成人格化回复”。待用户确认产品形象与逻辑链是否一致。
- (direction) 用户反馈当前架构提问过于专业、不具体。后续 coaching 改为用真实生活场景和期望回复做 elicitation，由主 agent 负责把行为回答翻译成架构约束，不再要求用户直接判断职责边界或算法术语。
- (direction) 正式开发流程采用产品守门 + 架构提案 + 用户裁决的评审方式；architecture 阶段由 Product Manager John 守护 SPEC 与 companions，由 Architect Winston 提出架构取舍，用户只对可见行为与权衡做裁决。使用 bmad-party-mode 机制，不重开产品愿景，也不把技术细节判断转嫁给用户。
- (constraint) 产品守门人 John 与架构师 Winston 第一轮达成：不能接受“所有 CAP 通过但用户明显继续分享时 Alice 机械收尾”的客服式体验。是否进入长聊不能依赖用户明确说出“陪我聊”；对话业务持有最终节奏，算法按轮报告沟通意愿及不确定性并允许后续行为推翻前判断，短回应必须能自然转成长聊。用户本人对真实对话是否感到被接住拥有最终判据。
- (direction) 用户明确不接受把中间架构问题抛回给自己。产品-架构 Party 必须先完成内部讨论，主 agent 提供完整对话纪要、明确结论、未决分歧与代价，再交用户以 Boss 身份接受、否决或指出不符合点。用户不需要替 Agent 分析技术取舍或回答实现问题。
- (decision) 业务负责整轮编排与爱丽丝最终表达。单轮流程固定为：接收请求 -> 业务向记忆端请求召回 -> 记忆端执行检索/重排序/自定义算法并返回高优先级记忆证据 -> 业务统一拼接稳定人格 Prompt、用户资料、近期对话与召回记忆 -> 交给 Agent 生成最终回复。记忆模块不生成最终人格文案。Prompt 作为稳定契约，不随意修改；变更需走契约评审和验证。所有关键阶段通过统一埋点记录，首版埋点用于观察与评估，不直接控制对话行为。
